从裸机大循环到 RTOS

一个大循环加中断能解决很多问题。什么时候它开始不够用？引入 RTOS 又要付出什么？

学完这一讲，你能

  • 说清裸机大循环的三个瓶颈
  • 列出 RTOS 提供的四类能力
  • 判断项目是否真的需要 RTOS
  • 估算 RTOS 的 RAM / Flash 与复杂度代价

1.1一个大循环能走多远

大多数裸机程序长这样：

main_loop.c · 片段（裸机结构示意）C11
int main(void)
{
    board_init();
    for (;;) {
        read_sensor();       /* 可能要等 10 ms */
        update_display();    /* 可能要 30 ms */
        handle_uart();       /* 数据来了才需要处理 */
        feed_watchdog();
    }
}

它能工作，但有三个结构性瓶颈：

阻塞传染

任何一步等待，后面所有逻辑都被推迟。显示刷新 30 ms，串口响应就可能晚 30 ms。

响应不确定

最坏响应时间等于整个循环的时间，而不是某个事件的处理时间。

状态耦合

各模块共享一个大循环，靠全局变量和标志沟通，越加越乱。

1.2RTOS 提供的四样东西

能力解决什么问题FreeRTOS 中的对应物
并发抽象把“同时要做的事”写成独立函数任务（task）
调度决定现在运行谁，让等待不再阻塞别人调度器、优先级、tick
通信任务之间安全地传数据队列、任务通知、事件组
同步保护共享资源、等待事件信号量、互斥量、临界区

注意：RTOS 不提供“无限资源”，也不提供“硬实时保证”。它提供的是可分析的结构：你能说清每个任务的周期、优先级、阻塞点和最坏执行时间。

1.3代价：RAM、Flash 与复杂度

典型 Cortex-M 上的量级（具体取决于配置与编译器）
项目量级说明
内核 Flash6–12 KB取决于启用的功能（定时器、事件组、统计等）
内核 RAM1–3 KB就绪列表、TCB、空闲任务等
每个任务栈256 B – 2 KB由局部变量、调用深度决定
堆几 KB – 几十 KBconfigTOTAL_HEAP_SIZE，队列和任务都从这里分配
切换开销几十个周期保存/恢复上下文，Cortex-M 有硬件加速
工程习惯

先问“需不需要”，再问“用哪个”。一个 8 位 MCU、只有 2 KB RAM、逻辑就是“读传感器 → 串口发出去”，用 RTOS 往往得不偿失。反过来，如果有 3 个以上独立时序、需要阻塞等待、需要协议栈，RTOS 通常比手写状态机更省心。

1.4什么时候不需要 RTOS

  • 逻辑是严格的单一时序，没有并发等待。
  • RAM 极度紧张，任务栈的开销无法承受。
  • 响应时间要求可以用“中断 + 主循环”满足，且可预测。
  • 团队不熟悉并发调试，引入 RTOS 反而增加风险。

反过来，出现下面任意两条，就该认真考虑 RTOS：多个独立周期、需要阻塞等待、通信协议栈、需要优先级（紧急事件优先处理）、代码需要长期维护和扩展。

1.5最小可运行结构

main_rtos.c · FreeRTOS V10/V11C11
#include "FreeRTOS.h"
#include "task.h"

static void blink_task(void *arg)
{
    (void)arg;
    for (;;) {
        gpio_toggle(LED_PIN);
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    board_init();

    if (xTaskCreate(blink_task, "blink", 128, NULL, 2, NULL) != pdPASS) {
        for (;;) { }              /* 创建失败：停在这里，便于调试 */
    }

    vTaskStartScheduler();        /* 正常情况下不会返回 */
    for (;;) { }
}
实现细节

vTaskStartScheduler() 会创建空闲任务（idle task），如果启用了软件定时器还会创建定时器守护任务。空闲任务优先级最低（0），负责释放被删除任务的内存、执行 idle hook。它必须始终有机会运行，否则低优先级清理工作永远做不了。

本讲小结

  • 裸机大循环的三个瓶颈：阻塞传染、响应不确定、状态耦合。
  • RTOS 提供任务、调度、通信、同步四类能力。

任务与任务创建

任务函数为什么不能返回？栈深度 128 到底是 128 字节还是 512 字节？参数传局部变量为什么会出错？

学完这一讲，你能

  • 正确调用 xTaskCreate 并检查返回值
  • 解释栈深度以“字”为单位
  • 说明任务函数不能返回的原因
  • 避免参数生命周期与栈溢出问题

2.1任务函数的形状

task_shape.cC11
#include "FreeRTOS.h"
#include "task.h"

static void my_task(void *arg)
{
    /* 初始化：只在任务第一次运行时执行 */
    int *config = (int *)arg;

    for (;;) {
        /* 循环体：任务的主体 */
        vTaskDelay(pdMS_TO_TICKS(100));
    }

    /* 永远不要执行到这里 */
    vTaskDelete(NULL);
}

三个硬性要求：

签名固定　void (*)(void *)，参数是一个 void *，返回值是 void。
不能返回　返回意味着任务函数退出，但任务没有“调用者”可以返回。必须死循环，或者显式 vTaskDelete(NULL)。
栈上别放大对象　任务栈通常只有几百字节到几 KB，大数组请用静态分配或堆。

2.2xTaskCreate 的六个参数

create.cC11
BaseType_t xTaskCreate(
    TaskFunction_t        pxTaskCode,   /* 任务函数 */
    const char * const    pcName,       /* 名字，仅用于调试 */
    configSTACK_DEPTH_TYPE usStackDepth,/* 栈深度，单位是“字” */
    void * const          pvParameters, /* 传给任务的参数 */
    UBaseType_t           uxPriority,   /* 优先级，数字越大越高 */
    TaskHandle_t * const  pxCreatedTask /* 返回句柄，可为 NULL */
);
参数注意点
usStackDepth单位是 StackType_t 的个数，不是字节。Cortex-M 上 StackType_t 是 uint32_t，所以 128 表示 512 字节。
pvParameters只是把指针存起来，不会复制所指对象。传局部变量地址会在任务启动前失效。
uxPriority范围 0 到 configMAX_PRIORITIES - 1；数值越大优先级越高。
返回值pdPASS 成功；errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY 表示堆不够。
易错

“栈深度 128”被理解成 128 字节，是最常见的误解之一。实际字节数 = usStackDepth * sizeof(StackType_t)。在 Cortex-M 上是 4 倍关系，在 8 位 AVR 上是 1 倍，在 16 位 MSP430 上是 2 倍。

2.3创建、检查、再使用

create_check.cC11
#include "FreeRTOS.h"
#include "task.h"

#define TASK_STACK_WORDS  256          /* 1024 字节（Cortex-M） */
#define TASK_PRIO         3

static TaskHandle_t g_worker;

void app_start(void)
{
    BaseType_t ok = xTaskCreate(worker_task, "worker", TASK_STACK_WORDS,
                                NULL, TASK_PRIO, &g_worker);
    if (ok != pdPASS) {
        /* 不要静默继续：记录错误、点亮故障灯、复位 */
        fatal_error(ERR_TASK_CREATE);
    }
}

句柄的用途：删除任务、改变优先级、给任务发通知、查询状态。如果不需要，传 NULL 即可。

2.4静态创建：不用堆

create_static.cC11
#include "FreeRTOS.h"
#include "task.h"

static StaticTask_t g_task_buf;
static StackType_t  g_task_stack[256];

void app_start_static(void)
{
    TaskHandle_t h = xTaskCreateStatic(worker_task, "worker", 256, NULL, 3,
                                       g_task_stack, &g_task_buf);
    configASSERT(h != NULL);
}

静态创建要求 configSUPPORT_STATIC_ALLOCATION = 1，并且需要自己提供空闲任务和定时器任务的内存（如果启用）。好处是链接期就能确定 RAM 占用，没有堆分配失败的风险。

工程习惯

安全关键或长期运行的设备，优先静态创建：内存占用可预测，不会因为碎片在运行几个月后突然创建失败。原型阶段用动态创建更方便，量产前再评估是否切换。

2.5删除任务

delete.cC11
/* 任务删除自己：传入 NULL */
vTaskDelete(NULL);

/* 删除别的任务：需要句柄 */
if (g_worker != NULL) {
    vTaskDelete(g_worker);
    g_worker = NULL;
}
实现细节

删除任务时，它占用的栈和 TCB 不会立刻释放，而是由空闲任务回收。如果程序不停地创建和删除任务，而空闲任务得不到运行机会，内存就会持续减少。这是“动态创建任务”最常见的隐性泄漏。

状态、优先级与调度

任务只有四种状态。调度器每次切换都在回答一个问题：现在最该运行的是谁？

学完这一讲，你能

  • 画出任务四状态迁移图
  • 区分抢占式调度与时间片轮转
  • 解释优先级数值与硬件中断优先级的不同
  • 说明调度不提供硬实时保证

3.1任务只有四种状态

状态含义怎么进入怎么离开
Running正在使用 CPU被调度器选中被抢占、阻塞、挂起、删除
Ready可运行，但没轮到创建、被唤醒、被恢复被调度、被挂起
Blocked在等事件或超时vTaskDelay、队列/信号量带超时的等待事件到达、超时
Suspended被显式暂停vTaskSuspendvTaskResume，无超时

3.2调度器怎么选下一个任务

FreeRTOS 为每个优先级维护一个就绪列表，并用一个位图记录“哪些优先级有任务就绪”。调度时找最高的非空优先级，取该列表的第一个任务。

抢占　如果新就绪的任务优先级高于当前任务，立刻切换（configUSE_PREEMPTION = 1）。
时间片　同优先级任务之间按 tick 轮转（configUSE_TIME_SLICING = 1）。
阻塞　当前任务阻塞时，调度器立刻选下一个就绪任务，不让 CPU 空转。
实现细节

FreeRTOS 的优先级数值越大越高，0 是最低（空闲任务）。Cortex-M 的硬件中断优先级则相反：数值越小越高。这两套规则经常被混淆，配置中断优先级时要特别小心（第 9 讲展开）。

动手看

抢占式调度时间轴

三个任务：H（优先级 3，每 4 tick 运行 1 tick）、M（优先级 2，每 8 tick 运行 2 tick）、L（优先级 1，始终就绪）。单步或播放，看 CPU 归谁。

t = 0

H 一旦就绪就立刻抢占 M 和 L；同优先级才会轮转。L 只能捡空隙运行，这就是“低优先级饥饿”的雏形。

3.3调度不是“硬实时保证”

FreeRTOS 是优先级抢占式内核，它能保证“更高优先级的就绪任务会先运行”，但不能保证“任务一定在某个时刻前完成”。原因至少有三类：

  • 临界区：关中断期间，高优先级任务也无法运行。
  • 中断延迟：中断响应受当前指令、优先级屏蔽影响。
  • 执行时间波动：缓存、分支预测、DMA 争用都会让最坏执行时间大于平均值。
标准怎么说

FreeRTOS 不声称自己是“硬实时认证内核”。要做硬实时分析，需要测量每个任务的最坏执行时间（WCET）、计算响应时间、考虑阻塞时间，并留足余量。RTOS 只是让这些分析可能，不是替你做完了。

3.4优先级怎么分配

任务类型建议优先级理由
安全/故障处理最高必须立刻响应，且执行时间短
硬实时控制高截止期最紧，周期固定
通信/协议栈中有一定实时性，但可容忍几十 ms
数据处理/显示低计算量大，可被抢占
日志/统计最低（高于 idle）后台工作，不能影响主逻辑

延时、节拍与周期任务

1 tick 不一定等于 1 ms；相对延时会累积漂移；周期任务要用绝对时间基准。

学完这一讲，你能

4.1tick：内核的心跳

FreeRTOS 需要一个周期性的时基来推进延时、超时和时间片。这个时基由硬件定时器（通常是 SysTick）产生，频率由 configTICK_RATE_HZ 决定。

易错

vTaskDelay(100) 的参数是 tick 数，不是毫秒。在 100 Hz 的配置下，它延时 1 秒，不是 100 ms。要么用 pdMS_TO_TICKS(100)，要么在注释里写清楚单位。

4.2相对延时：为什么会漂移

drift.cC11
for (;;) {
    do_work();                       /* 假设耗时 3 ms */
    vTaskDelay(pdMS_TO_TICKS(10));   /* 再等 10 ms */
}

实际周期不是 10 ms，而是 3 ms + 10 ms = 13 ms，再加上调度延迟。每轮都多出 3 ms，100 轮就偏了 300 ms。这叫累积漂移。

4.3vTaskDelayUntil：固定周期

periodic.cC11
#include "FreeRTOS.h"
#include "task.h"

static void sample_task(void *arg)
{
    (void)arg;
    TickType_t last = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(10);

    for (;;) {
        do_sample();                        /* 必须短于 period */
        vTaskDelayUntil(&last, period);     /* 按绝对时间安排下一次唤醒 */
    }
}

周期执行时间 + 延时固定 period

适用一次性等待、非周期任务固定采样率、控制周期
超时—如果执行超过 period，会立刻返回并落后，需要检测
实现细节

vTaskDelayUntil 不会“追赶”错过的周期。如果某次执行超过 period，下一次会立刻返回，last 仍然按 period 递增，于是任务持续落后。需要检测这种情况（比较当前 tick 与 last），并决定是跳过错过的周期还是报警。

4.4抖动、漂移与精度

  • 抖动：单次唤醒相对理想时刻的偏差，通常由中断延迟、调度延迟、临界区造成。
  • 漂移：长期平均周期偏离目标，通常由相对延时或时钟源误差造成。
  • 分辨率：最小可表达的时间是 1 tick；小于 1 tick 的延时可能被换算成 0，需要自己加 1 或提高 tick 频率。

需要微秒级精度时，不要指望 RTOS 的 tick：用硬件定时器 + 输入捕获/比较，或者用高分辨率定时器做时间戳，RTOS 只负责任务调度。

4.5低功耗：tickless idle

默认配置下，即使没有任务要运行，tick 中断也会每 1 ms 唤醒 CPU。对电池设备，这很浪费。FreeRTOS 提供 tickless 模式（configUSE_TICKLESS_IDLE），在空闲时关闭 tick 中断，直到下一个任务需要唤醒。

工程习惯

tickless 模式需要移植层实现“进入低功耗、按到期时间唤醒”，并且会引入额外的唤醒误差。先用默认模式把功能跑通，再评估功耗优化；不要一上来就开 tickless，否则调试会变复杂。

队列：有界的数据传送带

队列不是共享内存，也不是无限缓存。它按值复制、有固定长度，满了要等待或放弃。

5.1队列不是共享变量

队列是一段固定长度的缓冲区，每个元素大小固定。发送时按值复制进去，接收时按值复制出来。它解决的是“有界传递 + 阻塞等待”，不是“共享内存”。

按值复制发送的是数据的副本发送方可以立刻复用原缓冲区；但大结构体复制开销大
固定长度创建时确定，不能动态扩容满了必须等待或丢弃，策略要显式设计
FIFO默认先进先出也有 xQueueSendToFront 用于插队
线程安全内部已处理临界区不需要额外加锁

5.2创建、发送、接收

queue_basic.cC11
#include "FreeRTOS.h"
#include "queue.h"

typedef struct {
    uint16_t id;
    int32_t  value;
} sample_t;

static QueueHandle_t g_samples;

void app_init(void)
{
    /* 长度 8，每个元素 sizeof(sample_t) */
    g_samples = xQueueCreate(8, sizeof(sample_t));
    configASSERT(g_samples != NULL);
}

/* 生产者任务 */
static void producer(void *arg)
{
    (void)arg;
    uint16_t id = 0;
    for (;;) {
        sample_t s = { .id = id++, .value = read_adc() };

        /* 最多等 10 ms；队列满则返回 errQUEUE_FULL */
        if (xQueueSend(g_samples, &s, pdMS_TO_TICKS(10)) != pdPASS) {
            g_drop_count++;              /* 丢弃并计数，不要静默 */
        }
        vTaskDelay(pdMS_TO_TICKS(20));
    }
}

/* 消费者任务 */
static void consumer(void *arg)
{
    (void)arg;
    sample_t s;
    for (;;) {
        /* 最多等 100 ms；超时返回 pdFALSE */
        if (xQueueReceive(g_samples, &s, pdMS_TO_TICKS(100)) == pdPASS) {
            process(&s);
        } else {
            /* 超时：可以做健康检查、心跳、低功耗 */
        }
    }
}
实现细节

队列满时，xQueueSend 会把当前任务放入“等待发送”的阻塞列表；一旦有空间，最高优先级的等待者被唤醒。等待时间以 tick 为单位，0 表示不等待，portMAX_DELAY 表示无限等待（需要 INCLUDE_vTaskSuspend = 1）。

真实调用还会带超时参数：等待期间任务处于 Blocked，超时后返回 errQUEUE_FULL 或 pdFALSE。

5.3队列长度怎么定

队列长度的本质是“允许积压多少”。它由三个量决定：

生产速率　每秒产生多少元素（突发时可能是平均值的数倍）。
消费速率　每秒处理多少元素，最坏情况下的处理时间。
可容忍延迟　从产生到处理，最多能等多久。

一个粗略公式：长度 ≥ (生产速率 - 消费速率) × 最大阻塞时间。如果生产长期快于消费，队列再大也会满——那不是队列长度问题，是系统过载。

易错

把指针放进队列来“避免复制大结构体”，但指针指向的是发送方的栈或会被复用的缓冲区。接收方拿到指针时，内容可能已经变了。要么复制数据，要么用内存池 + 明确的所有权转移。

6.1信号量回答的是“有没有 / 有几个”

信号量不携带数据。它只有一个计数值，任务通过“取”和“给”来同步。二值信号量的值只有 0 和 1，计数信号量可以是 0 到最大值。

二值

事件是否发生

中断发生 → 任务处理。给一次、取一次，之后回到 0。适合“一次性事件通知”。

计数

还剩几个资源 / 发生了几次

初值为 N，取一次减一，给一次加一。适合“缓冲区槽位”“事件累计次数”。

7.2优先级反转：高优先级被低优先级“拖住”

场景：低优先级任务 L 持有互斥量，高优先级任务 H 需要同一把锁，于是 H 阻塞。此时中优先级任务 M 就绪——M 的优先级高于 L，于是 M 抢占 L，L 无法继续执行，也就无法释放锁。结果：H 在等 M 跑完。

现实中反转往往表现为“偶尔卡顿几百毫秒”，很难复现；一旦出现，先查持锁任务是否被中优先级任务抢占。

7.3死锁：互相等对方的锁

8.1事件组：等“多个条件同时满足”

事件组是一组二进制位，每个位代表一个事件。任务可以等待“任意一位置位”或“所有指定位置位”。它适合“传感器就绪 + 网络连接 + 配置加载完成，三者都好了才开始采集”这类条件。

#include "event_groups.h"

#define BIT_SENSOR_READY  (1u << 0)
#define BIT_NET_READY     (1u << 1)
#define BIT_CONFIG_LOADED (1u << 2)

static EventGroupHandle_t g_events;

void app_init(void)
{
    g_events = xEventGroupCreate();
    configASSERT(g_events != NULL);
}

static void startup_task(void *arg)
{
    (void)arg;
    const EventBits_t need = BIT_SENSOR_READY | BIT_NET_READY | BIT_CONFIG_LOADED;

    EventBits_t got = xEventGroupWaitBits(
        g_events,
        need,
        pdTRUE,        /* 退出时清除这些位 */
        pdTRUE,        /* 等待所有位都置位 */
        pdMS_TO_TICKS(5000));

    if ((got & need) == need) {
        start_normal_operation();
    } else {
        handle_startup_timeout(got);     /* 超时：能知道还差哪一位 */
    }
}

{
    BaseType_t woken = pdFALSE;
    xEventGroupSetBitsFromISR(g_events, BIT_SENSOR_READY, &woken);
    portYIELD_FROM_ISR(woken);
}

9.2pxHigherPriorityTaskWoken 与 yield

isr_queue.cC11
static void UART_IRQHandler(void)
{
    BaseType_t woken = pdFALSE;          /* 必须先初始化为 pdFALSE */
    uint8_t byte = uart_read();

    xQueueSendFromISR(g_rx_q, &byte, &woken);

    /* 如果刚才的发送唤醒了更高优先级任务，退出中断时立刻切换 */
    portYIELD_FROM_ISR(woken);
}

为什么需要这个参数？中断结束时，硬件会恢复被中断的任务。如果刚才的操作让一个更高优先级任务就绪，内核需要“改主意”，在中断退出时切换到它。这个参数就是告诉移植层“要不要切”。

易错

忘记初始化 woken = pdFALSE，或者多个 FromISR 调用共用一个变量却在中途重置，都会导致“该切换时没切换”，表现为高优先级任务延迟运行，甚至偶尔卡死。

9.3Cortex-M 的中断优先级陷阱

FreeRTOS 在 Cortex-M 上要求：调用 FreeRTOS API 的中断，其硬件优先级数值必须 ≥ configMAX_SYSCALL_INTERRUPT_PRIORITY（数值越大，优先级越低）。

临界区、竞争条件与线程安全

counter++ 不是原子操作。临界区、调度器挂起和原子指令，各自解决不同层面的问题。

学完这一讲，你能

  • 识别任务间的竞争条件
  • 正确使用 taskENTER_CRITICAL
  • 区分关中断与挂起调度器
  • 判断一个函数是否可重入

10.1一行 C 不是原子操作

g_counter++ 编译后是“读 → 加 → 写”。两个任务交替执行时，可能都读到 5，各自写回 6，最终少加一次。这类问题叫竞争条件（race condition）。

race.cC11
static uint32_t g_counter;

void task_a(void *arg) { (void)arg; for (;;) { g_counter++; vTaskDelay(1); } }
void task_b(void *arg) { (void)arg; for (;;) { g_counter++; vTaskDelay(1); } }
易错

加 volatile 不能解决竞争。它只保证“每次都去内存读”，不保证“读和写之间不被打断”。竞争需要互斥或原子操作。

10.2临界区：短暂关闭调度与中断

critical.cC11
#include "FreeRTOS.h"
#include "task.h"

void update_counter(void)
{
    taskENTER_CRITICAL();
    g_counter++;                 /* 这期间不会被任务切换或受管中断打断 */
    taskEXIT_CRITICAL();
}
API作用范围能否嵌套适用
taskENTER_CRITICAL屏蔽受管中断 + 禁止调度是（计数）几行代码的原子更新
vTaskSuspendAll只禁止任务切换，中断仍运行是较长的只读遍历、避免中断延迟
portENTER_CRITICAL更底层，移植相关视端口内核/驱动内部
实现细节

在 Cortex-M 端口上，taskENTER_CRITICAL() 会把 BASEPRI 设为 configMAX_SYSCALL_INTERRUPT_PRIORITY，从而屏蔽“允许调用 FreeRTOS API 的中断”，但不屏蔽更高优先级的中断。所以临界区并不能防止所有中断修改数据——那些高优先级中断本来就不该碰共享数据。

10.3关中断 vs 挂起调度器

taskENTER_CRITICAL

更“硬”的保护

连中断都挡在外面。适合几行代码的读改写、链表插入。时间必须极短，否则中断延迟变大。

vTaskSuspendAll

只挡任务切换

中断照常运行，所以中断仍可能修改数据。适合“遍历一个不会被中断修改的结构”，或避免长时间关中断。

软件定时器

软件定时器不是硬件定时器，它的回调运行在一个普通任务里——所以不能阻塞，也不精确。

学完这一讲，你能

  • 创建一次性与周期定时器

  • 在回调里只做轻量工作
  • 判断何时该用硬件定时器

11.1软件定时器不是硬件定时器

FreeRTOS 的软件定时器由定时器守护任务（timer service task）统一管理。定时器到期时，守护任务调用你的回调。回调运行在任务上下文，不是中断上下文。

软件定时器硬件定时器
精度受 tick 与守护任务调度影响可达纳秒级
数量几乎不限（受 RAM 限制）受外设数量限制
回调上下文守护任务中断
适用超时、心跳、周期性业务PWM、输入捕获、精确采样

11.3回调里不能做什么

不要做原因替代

长时间计算同上把工作交给专用任务

11.4精度与漂移

周期定时器的“周期”是两次到期之间的 tick 数，但回调执行时间、守护任务被更高优先级任务抢占，都会让实际间隔变长。它不累积相对误差（内核按绝对到期时间排队），但会有抖动。

  • 需要毫秒级稳定周期：用硬件定时器中断 + 任务通知。
  • 需要“几秒后提醒”：软件定时器足够。
  • 需要大量定时器：软件定时器比硬件定时器更省外设。

12.1五种堆方案

FreeRTOS 把 pvPortMalloc / vPortFree 的实现放在 heap_x.c 里，由你选择其中一个加入工程。

方案能释放吗碎片适用
heap_1不能无只在启动时创建任务/队列，之后不释放
heap_2能不会合并相邻块旧项目；新项目不建议
heap_3能取决于 libc malloc使用编译器自带 malloc，需实现线程安全
heap_4能会合并相邻空闲块通用首选
heap_5能同 heap_4，多区域RAM 不连续（如内部 + 外部 SRAM）
工程习惯

长期运行的设备优先 heap_4（合并碎片）或静态分配（完全不依赖堆）。heap_2 不合并相邻空闲块，反复分配/释放后很容易“总量够但最大块不够”。

12.2堆有多大，谁在用

实现细节

xPortGetMinimumEverFreeHeapSize 只有 heap_4 和 heap_5 提供。它记录历史最低空闲量，是判断“堆是否够用”的关键指标——当前空闲很多，不代表高峰时没接近耗尽。

任务栈要容纳：局部变量、函数调用返回地址、保存的寄存器、中断嵌套时的上下文。栈太小会踩坏相邻内存，表现为“变量莫名其妙变了”或 HardFault。

12.4栈大小怎么估

先给足　按经验给一个偏大的值（例如 256–512 字），先让功能跑起来。
测高水位　跑遍所有分支、最坏输入、中断嵌套场景，读 uxTaskGetStackHighWaterMark。
留余量　保留至少 25%–30% 余量，再把栈调小；不要压到“刚好不溢出”。
回归　每次加功能后重新测，尤其是增加了深层调用或大局部数组。
易错

只在“正常路径”测高水位是不够的。错误处理、异常输入、通信断开重连这些路径往往调用更深、局部变量更多，才是栈的真正峰值。

12.5碎片：为什么“总量够却分配失败”

假设堆里有 3 个 100 字节的空闲块，但你要分配 250 字节——总量 300 够，却没有连续的 250 字节。这就是外部碎片。

  • heap_4 会合并相邻空闲块，能缓解但不能消除碎片。
  • 反复创建/删除不同大小的任务和队列，最容易产生碎片。
  • 长期运行的系统，优先“启动时一次性分配，运行期不再分配”。
正确做法

把 xPortGetMinimumEverFreeHeapSize 和分配失败计数一起上报。如果最小值持续下降，说明有泄漏；如果最小值稳定但分配仍失败，说明碎片严重。

13.2死锁的排查

死锁时系统往往“安静地停住”：没有崩溃，没有日志，只是什么都不发生。排查步骤：

确认是否死锁　用调试器暂停，看各任务卡在哪个函数；如果都卡在 xSemaphoreTake，高度怀疑。
找锁的持有者　FreeRTOS 的互斥量有所有者；检查是谁拿了锁却没释放。
看加锁顺序　两个任务是否以相反顺序获取两把锁。
加超时与日志　把 portMAX_DELAY 改成有限超时，记录失败点。
deadlock_fix.cC11
/* 统一顺序：永远先 m1 后 m2 */
if (xSemaphoreTake(m1, pdMS_TO_TICKS(50)) != pdTRUE) {
    return ERR_BUSY;
}
if (xSemaphoreTake(m2, pdMS_TO_TICKS(50)) != pdTRUE) {
    xSemaphoreGive(m1);                 /* 拿不到第二把，释放第一把 */
    return ERR_BUSY;
}
/* ... */
xSemaphoreGive(m2);
xSemaphoreGive(m1);

13.3饥饿与 CPU 利用率

如果高优先级任务永远就绪（例如一个没有阻塞的 for(;;) 循环），低优先级任务永远得不到 CPU。这不是 bug，是设计问题。

  • 每个任务都必须有阻塞点（延时、等队列、等信号量）。
  • 计算密集型任务要主动让出，或放到最低优先级。
  • 用运行时统计看每个任务占了多少 CPU。
stats.cC11
/* 需要 configGENERATE_RUN_TIME_STATS = 1，并提供高精度计时 */
char buf[512];
vTaskGetRunTimeStats(buf);      /* 每个任务的运行时间与占比 */
printf("%s\n", buf);

vTaskList(buf);                 /* 任务状态、优先级、剩余栈、序号 */
printf("%s\n", buf);
实现细节

vTaskGetRunTimeStats 需要一个比 tick 更细的计时源（通常是另一个定时器），通过 portCONFIGURE_TIMER_FOR_RUN_TIME_STATS 和 portGET_RUN_TIME_COUNTER_VALUE 接入。只有 tick 计时的话，分辨率太粗。

13.4栈溢出的现象与定位

栈溢出最迷惑人的地方是它不一定立刻崩溃：溢出的数据可能踩到相邻任务的栈或 TCB，表现为“某个无关变量变了”“任务突然不跑了”。

配置行为优缺点
configCHECK_FOR_STACK_OVERFLOW = 1切换时检查栈指针是否越界开销小，但只能发现“已经越界”
= 2 additionally 检查栈末尾的魔术字更可靠，需要预填模式
高水位运行后查看剩余量不能发现瞬时峰值
工程习惯

发布版本也保留栈溢出钩子，但钩子里不要 printf（栈可能已经坏了）。最稳的做法是：点亮故障灯、把任务名写入保留 RAM（不掉电区域）、触发看门狗复位。

13.5configASSERT 与看门狗

assert.cC11
/* 在 FreeRTOSConfig.h 中定义，参数非法时立刻停机 */
#define configASSERT(x)  do { if (!(x)) { taskDISABLE_INTERRUPTS(); \
                                           fault_handler(__FILE__, __LINE__); } } while (0)

configASSERT 能抓住大量“参数非法、优先级越界、队列句柄为空”的问题。开发阶段一定打开；发布版本可以保留（停机 + 记录），也可以改成复位。

看门狗是最后一道防线：监控任务定期“喂狗”，如果某个关键任务卡死，系统自动复位。注意喂狗应该在所有关键任务都健康时进行，而不是随便找个最低优先级任务喂。

13.6五个常见误区

误区事实
“优先级越高，系统越实时”优先级只决定谁先运行；实时性取决于最坏执行时间与阻塞时间
“加了互斥量就不会有并发问题”还要考虑死锁、持锁时间、ISR 访问
“volatile 能替代锁”它不保证原子性，也不保证顺序
“队列越长越安全”长队列增加延迟和 RAM；过载时照样满
“RTOS 会自动保证实时”它只提供机制，分析和设计仍要自己做

  2. 高优先级任务偶发延迟 200 ms，可能是什么原因？
  3. 如何用运行时统计证明某个任务占用了 95% CPU？
  4. 设计一个“关键任务都健康才喂狗”的方案。
参考答案与思路

1. 暂停看各任务栈：都卡在等锁 → 死锁；高优先级任务一直 Running、低优先级从未运行 → 饥饿。

2. 优先级反转（持锁任务被中优先级抢占）、临界区过长、中断关闭过久、队列/内存分配阻塞。

3. 开 configGENERATE_RUN_TIME_STATS，调用 vTaskGetRunTimeStats，看该任务的百分比与绝对时间。

4. 每个关键任务定期置一个事件位；监控任务等齐所有位后喂狗并清位；任何一个任务超时未置位，就不喂狗，让系统复位。

自测：低优先级任务长期得不到运行，最可能的原因是？

这是典型的饥饿：高优先级任务没有阻塞点，调度器永远选它。解决办法是给高优先级任务加阻塞点，或重新评估优先级与任务划分。

本讲小结

  • 死锁、反转、饥饿、栈溢出都会表现成“卡住”，但根因不同。
  • 死锁靠加锁顺序、超时与日志定位。
  • 饥饿靠运行时统计与“每个任务都要阻塞”来避免。
  • 栈溢出要用高水位 + 溢出钩子 + 最坏路径测试。
  • configASSERT 与看门狗是最后两道防线。

14.1需求与任务划分

目标：每 10 ms 采一次传感器，做滑动平均，打包后通过串口/网络发出；同时监控系统健康（队列丢弃、栈余量、堆余量），异常时进入安全状态。

任务划分（优先级数值越大越高）
任务优先级周期/触发最坏执行职责
sensor410 ms 周期1.5 ms读 ADC，写入原始队列
process3队列到达2 ms滤波、换算、打包
comm2队列到达8 ms（含阻塞发送）发送帧，处理重试
monitor11 s 周期0.5 ms统计、健康检查、喂狗

优先级按“周期越短越高”分配。comm 的最坏执行最长，所以放在 process 之下；即使它阻塞，也不会拖住采样。

14.3核心代码骨架

工程习惯

下面的代码是目标板结构示例，依赖 FreeRTOS 与具体硬件接口，未在主机上编译验证。它展示的是任务划分、队列策略与错误处理方式，不是可直接烧录的完整工程。

app.c · 目标板示例（未在主机验证）C11
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "event_groups.h"

#define Q_RAW_LEN   8
#define Q_TX_LEN    4

typedef struct { uint16_t raw; uint32_t t_ms; } sample_t;
typedef struct { int16_t value; uint32_t t_ms; uint8_t seq; } frame_t;

static QueueHandle_t g_q_raw, g_q_tx;
static EventGroupHandle_t g_health;
static volatile uint32_t g_drop_raw, g_drop_tx;

#define HEALTH_SENSOR  (1u << 0)
#define HEALTH_PROC    (1u << 1)
#define HEALTH_COMM    (1u << 2)

static void sensor_task(void *arg)
{
    (void)arg;
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        sample_t s = { .raw = adc_read(), .t_ms = (uint32_t)xTaskGetTickCount() };

        /* 采样不能被阻塞太久：最多等 2 ms，满则丢弃并计数 */
        if (xQueueSend(g_q_raw, &s, pdMS_TO_TICKS(2)) != pdPASS) {
            g_drop_raw++;
        }

        xEventGroupSetBits(g_health, HEALTH_SENSOR);
        vTaskDelayUntil(&last, pdMS_TO_TICKS(10));
    }
}

static void process_task(void *arg)
{
    (void)arg;
    static int32_t window[8];
    static size_t idx;
    sample_t s;

    for (;;) {
        if (xQueueReceive(g_q_raw, &s, portMAX_DELAY) != pdPASS) {
            continue;
        }

        window[idx++ % 8] = s.raw;
        int32_t sum = 0;
        for (size_t i = 0; i < 8; i++) {
            sum += window[i];
        }

        frame_t f = { .value = (int16_t)(sum / 8), .t_ms = s.t_ms, .seq = (uint8_t)idx };
        if (xQueueSend(g_q_tx, &f, pdMS_TO_TICKS(5)) != pdPASS) {
            g_drop_tx++;
        }
        xEventGroupSetBits(g_health, HEALTH_PROC);
    }
}

static void comm_task(void *arg)
{
    (void)arg;
    frame_t f;
    for (;;) {
        if (xQueueReceive(g_q_tx, &f, portMAX_DELAY) != pdPASS) {
            continue;
        }

        /* 发送可能阻塞：允许 50 ms，失败则重试一次 */
        if (link_send(&f, sizeof f, pdMS_TO_TICKS(50)) != 0) {
            (void)link_send(&f, sizeof f, pdMS_TO_TICKS(50));
        }
        xEventGroupSetBits(g_health, HEALTH_COMM);
    }
}

static void monitor_task(void *arg)
{
    (void)arg;
    const EventBits_t all = HEALTH_SENSOR | HEALTH_PROC | HEALTH_COMM;

    for (;;) {
        vTaskDelay(pdMS_TO_TICKS(1000));

        EventBits_t bits = xEventGroupClearBits(g_health, all);
        size_t heap_min = xPortGetMinimumEverFreeHeapSize();

        if ((bits & all) == all && heap_min > 1024) {
            watchdog_feed();                 /* 全部健康才喂狗 */
        } else {
            enter_safe_mode(bits, heap_min); /* 记录哪一项不健康 */
        }
    }
}

14.4队列长度与丢弃策略

队列长度满时策略理由
q_raw8丢弃新样本，计数采样是周期性的，旧数据比新数据更没价值；不能阻塞采样
q_tx4丢弃新帧，计数通信拥塞时保留最近的几帧，避免无限积压

两个队列都不阻塞生产者太久：采样任务最多等 2 ms，处理任务最多等 5 ms。超过就丢弃并计数，由监控任务上报。这比“无限等待”更可控。

14.5时序与可调度性检查

任务周期最坏执行CPU 占比
sensor10 ms1.5 ms15%
process10 ms（跟随采样）2.0 ms20%
comm约 10 ms8.0 ms（含阻塞）取决于链路
monitor1000 ms0.5 ms<1%
idle——剩余

注意 comm 的 8 ms 里大部分是“阻塞等待发送完成”，并不占 CPU。真正要算的是CPU 占用，不是墙上时间。如果 comm 的发送是忙等，就会把 CPU 吃光——这也是为什么驱动要提供阻塞式/中断式发送。

易错

把所有任务都设成高优先级，等于没有优先级。优先级的意义是“在冲突时谁先运行”，如果每个任务都“很重要”，系统就无法在过载时保住关键任务。

14.6测试与验收

  • 空载：4 个任务都运行，CPU 占用 < 30%
  • 满负载：采样 10 ms 不丢帧，队列丢弃计数为 0
  • 通信断开：q_tx 满后按策略丢弃，系统不卡死，恢复后能继续
  • 注入错误：传感器返回非法值，process 不崩溃
  • 连续运行 24 h：堆最小值不持续下降，无栈溢出
  • 看门狗：人为挂起 comm 任务，系统应在超时后复位

  2. 给 comm 任务加“指数退避重试”，最多 3 次。
  3. 设计一个“配置更新”命令：通过队列发给 process，要求不阻塞采样。

参考答案与思路

1. 长度 2 只能吸收 20 ms 的抖动；只要 process 偶尔超过 20 ms，就会开始丢弃。适合“允许丢帧、但要低延迟”的场景。

2. 保存 backoff，失败后 vTaskDelay(backoff)，backoff = min(backoff*2, MAX)；成功则复位。注意 comm 阻塞期间 q_tx 会积压，要配合丢弃策略。

3. 单独建一个配置队列，process 在每次循环里非阻塞地检查配置队列；或者用事件组置位 + 共享配置结构（加互斥量）。

4. 开 configGENERATE_RUN_TIME_STATS，运行典型负载后打印统计，和 14.5 的估算对比。

自测：采样任务在队列满时应该？

采样任务的第一职责是“按时采样”。无限等待会破坏周期；队列本身不支持覆盖。正确做法是短超时 + 丢弃 + 计数，由监控任务上报。

本讲小结

  • 任务划分按“周期 + 职责”，优先级按截止期分配。
  • 队列长度与丢弃策略要显式设计，不能无限等待。
  • 监控任务旁路观察，全部健康才喂狗。
  • CPU 占用要按“实际执行时间”算，不是墙上时间。
  • 测试要覆盖空载、满载、断链、错误注入与长时间运行。
