网络基础与分层

一次网页访问，数据在发送方被一层层套上头部，在接收方又被一层层剥开。理解封装，就理解了一半网络。

学完这一讲，你能

  • 说清客户端/服务器模型
  • 区分 OSI 与 TCP/IP 分层
  • 描述封装与解封装过程
  • 知道每层典型的协议与设备

1.1两台机器说话，需要约定什么

网络通信的本质是“两台机器上的两个程序交换字节”。要让它可靠发生，至少要约定五件事：

怎么连　物理介质与接口（网线、Wi-Fi、光纤）。
怎么找到对方　地址（MAC、IP、域名）。
数据怎么切分　帧、包、段，各自的边界与校验。
丢了怎么办　确认、重传、超时、顺序。
字节是什么意思　应用层协议（HTTP、MQTT、自定义）。

把这些问题分层处理，就是网络架构的核心思想：每一层只解决一类问题，并向上提供接口。

1.2OSI 七层与 TCP/IP 四层

TCP/IP 四层OSI 对应典型协议典型设备/概念数据单位
应用层应用 / 表示 / 会话HTTP、DNS、MQTT、TLS浏览器、客户端、Broker消息
传输层传输TCP、UDP端口、套接字段（segment）/ 数据报
网络层网络IP、ICMP、ARP*路由器包（packet）
链路层数据链路 / 物理Ethernet、Wi-Fi、PPP交换机、网卡帧（frame）

* ARP 常被归到链路层与网络层之间，它把 IP 地址解析成 MAC 地址，不承载上层数据。

工程习惯

排障时先问“问题在哪一层”：网线没插是链路层，IP 配错是网络层，端口没监听是传输层，返回 404 是应用层。分层不是为了考试，是为了让你知道下一步该查什么。

1.3封装：一层套一层

发送数据时，每一层都会在数据前面加上自己的头部（有时还有尾部）。接收时再逐层剥掉。这个过程叫封装 / 解封装。

动手看

一条消息被套了多少层

点击“发送”，看应用数据如何被 TCP、IP、以太网依次加上头部；再点“接收”，看它如何被逐层剥开。

每层只关心自己的头部，不关心上层载荷的内容——这就是分层的价值。

1.4客户端与服务器

“客户端/服务器”不是指硬件，而是指角色：主动发起连接的一方是客户端，被动等待连接的一方是服务器。同一个程序可以既是客户端又是服务器。

角色典型行为例子
客户端知道服务器地址，主动连接，发请求浏览器、手机 App、ESP32 上报程序
服务器监听端口，接受连接，处理请求Web 服务器、MQTT Broker
对等（P2P）双方既发又收，角色对等局域网文件传输、部分音视频

服务器要同时服务多个客户端，通常用“每连接一个线程/协程”或“事件循环（epoll/kqueue）”。嵌入式设备资源有限，通常只做客户端，或者做轻量服务器（如配置页面）。

1.5一次访问，经过哪些设备

一次网页访问的简化路径text
浏览器 → 本机协议栈 → 网卡 → 交换机 → 路由器 → 运营商网络 → 目标服务器
   ↑                                                              ↓
   └──────────────── 响应沿相反路径返回 ─────────────────────────┘
  • 交换机工作在链路层，按 MAC 转发帧，不改变 IP。
  • 路由器工作在网络层，按 IP 前缀转发包，每跳都会改 MAC、减 TTL。
  • NAT 在路由器上改写源/目的 IP 与端口，让多台内网设备共享一个公网地址。

链路层 · 50 分钟 · ★★☆

以太网、MAC 与交换机

MAC 地址是网卡的身份证，交换机靠 MAC 表转发帧。广播域、冲突域这些词，其实都在描述“谁能听到谁”。

学完这一讲，你能

  • 解释 MAC 地址与以太网帧结构
  • 说明交换机如何学习与转发
  • 区分广播、单播与泛洪
  • 理解 VLAN 与广播域

2.1MAC 地址：网卡的身份证

MAC 地址 48 位，通常写成 00:1A:2B:3C:4D:5E。前 24 位是厂商前缀（OUI），后 24 位由厂商分配。它只在同一个局域网内有效，路由器不会把 MAC 带到互联网。

类型特征用途
单播第一个字节最低位为 0发给某一块网卡
广播FF:FF:FF:FF:FF:FFARP 请求、DHCP 发现
组播第一个字节最低位为 1视频流、IPv6 邻居发现
实现细节

每块网卡的 MAC 理论上全球唯一，但很多芯片允许软件修改（MAC 地址克隆/随机化）。虚拟机和容器更是随便配。所以不能把 MAC 当作安全凭证。

2.2以太网帧

Ethernet II 帧
字段长度说明
前导码 + SFD7 + 1 字节用于时钟同步，不算帧内容
目的 MAC6 字节可以是单播/广播/组播
源 MAC6 字节发送方网卡
类型/长度2 字节0x0800 = IPv4，0x0806 = ARP，0x86DD = IPv6
载荷46–1500 字节IP 包；不足 46 字节要填充
FCS4 字节CRC32 校验，错误帧直接丢弃

MTU（最大传输单元）通常是 1500 字节。IP 包超过 MTU 就要分片，或者由上层控制报文大小（TCP 的 MSS 就是据此协商的）。

2.3交换机怎么转发

学习　收到帧时，把“源 MAC + 入端口”记进 MAC 表。
查找　看目的 MAC 在表里有没有。
转发　有就只从对应端口发出（单播）。
泛洪　没有就从除入端口外的所有端口发出。
老化　表项一段时间不用就删除，适应设备移动。
查看本机 MAC 与邻居（Linux / Windows）bash

getmac /v                   # Windows：看 MAC
ip neigh                    # Linux：ARP/邻居表
arp -a                      # Windows：ARP 表

2.4冲突域与广播域

概念含义隔离设备
冲突域同时发送会冲突的范围交换机每个端口一个冲突域
广播域广播帧能到达的范围路由器 / VLAN

交换机隔离冲突域，但不隔离广播域：一个广播帧会被泛洪到所有端口。广播太多会占用带宽和 CPU，这时就用 VLAN 把一个物理交换机切成多个逻辑广播域。

工程习惯

嵌入式设备如果频繁发广播（例如设备发现协议），要考虑广播风暴的风险。能用量身定制的组播/单播，就不要用广播。

2.5VLAN 与 Trunk

VLAN 在以太网帧里插入 4 字节标签（802.1Q），用 12 位 VLAN ID 标识所属网络。交换机端口可以配置成：

  • Access：只属于一个 VLAN，接终端设备。
  • Trunk：承载多个 VLAN，接交换机/路由器，帧带标签。

对嵌入式设备来说，VLAN 通常是“网络管理员的事”；但如果你要接工业交换机、划分控制网与办公网，就需要知道设备该接 Access 口还是 Trunk 口。

动手练习 · 第 2 讲
  1. 为什么 MAC 地址不能跨路由器传递？
  2. 交换机收到未知目的 MAC 的帧会怎么做？
  3. 广播域和冲突域分别由什么设备隔离？
  4. MTU 1500 时，一个 3000 字节的 IP 包会怎样？
参考答案与思路

1. MAC 只在链路层本地有效；路由器每跳会重新封装成新的链路层帧，源/目的 MAC 都变成当前链路两端的地址。

2. 泛洪到除入端口外的所有端口，同时学习源 MAC。

3. 冲突域由交换机端口隔离；广播域由路由器或 VLAN 隔离。

4. 若 DF=0 则分成两个片；若 DF=1 则丢弃并返回 ICMP“需要分片”。

自测：交换机主要根据什么转发帧？

普通二层交换机看目的 MAC；路由器才看目的 IP；端口号是传输层概念，交换机不解析。

本讲小结

  • MAC 是链路层地址，只在本地链路有效。
  • 以太网帧包含源/目的 MAC、类型、载荷与 FCS。
  • 交换机学习源 MAC、按目的 MAC 转发、未知则泛洪。
  • 交换机隔离冲突域，路由器/VLAN 隔离广播域。
  • MTU 决定是否需要分片。
  • 我能读出以太网帧的关键字段
  • 我能解释交换机的学习与泛洪

网络层 · 60 分钟 · ★★★

IPv4、子网与 CIDR

IP 地址不是“设备编号”，而是“网络号 + 主机号”。掩码决定哪部分是网络，网关决定出网找谁。

学完这一讲，你能

  • 根据 IP 与掩码算出网络号、广播地址与可用范围
  • 用 CIDR 表示子网并划分子网
  • 解释默认网关的作用
  • 区分私有地址、回环与链路本地地址

3.1IP 地址 = 网络号 + 主机号

IPv4 地址 32 位，写成四段十进制（192.168.1.10）。它由两部分组成：网络号（在哪个网络）和主机号（网络里的哪台设备）。分界线由子网掩码决定。

一个 /24 的例子text
IP     192.168.1.10    11000000 10101000 00000001 00001010
掩码   255.255.255.0   11111111 11111111 11111111 00000000
网络号 192.168.1.0     前 24 位相同
广播   192.168.1.255   主机号全 1
可用   192.168.1.1 – 192.168.1.254
地址段用途说明
10.0.0.0/8私有企业内网，可用地址最多
172.16.0.0/12私有172.16–172.31
192.168.0.0/16私有家庭/小型办公最常见
127.0.0.0/8回环127.0.0.1 指本机
169.254.0.0/16链路本地DHCP 失败时自动配置
224.0.0.0/4组播视频、路由协议、mDNS

3.2CIDR：用 /n 表示掩码

/24 表示前 24 位是网络号，等价于 255.255.255.0。常见换算：

前缀掩码地址数可用主机数
/24255.255.255.0256254
/25255.255.255.128128126
/26255.255.255.1926462
/27255.255.255.2243230
/28255.255.255.2401614
/30255.255.255.25242（点对点链路）

主机数 = 2(32-n) - 2，减去网络地址和广播地址。 exceptions：/31 点对点链路（RFC 3021）可用 2 个地址，/32 表示单个主机路由。

动手看

子网计算器

输入 IP 和前缀，实时得到网络号、广播地址、可用范围与主机数，并显示二进制对齐过程。

网络地址 = IP 与掩码按位与；广播地址 = 网络地址 | ~掩码。这两个地址不能分配给主机。

3.3划分子网：为什么要借位

一个 /24 有 254 个可用地址。如果只有 20 台设备，剩下的地址就浪费了，而且所有设备在同一个广播域里。划分子网就是从主机号里借几位当网络号。

把 192.168.1.0/24 划成 4 个 /26text
子网 1：192.168.1.0/26    可用 .1  – .62
子网 2：192.168.1.64/26   可用 .65 – .126
子网 3：192.168.1.128/26  可用 .129 – .190
子网 4：192.168.1.192/26  可用 .193 – .254
工程习惯

规划地址时按“未来 2–3 年的设备数”留余量。把生产设备、办公设备、访客网络分到不同子网，既方便管理，也方便做访问控制。

3.4默认网关：出网找谁

主机发数据前先判断：目的 IP 和我在同一个子网吗？

  • 是：直接 ARP 找对方 MAC，发给它。
  • 否：发给默认网关（路由器的内网地址），由它继续转发。
查看本机地址与路由（Linux / Windows）bash
ip addr                     # Linux：地址与掩码
ip route                    # Linux：默认网关
ipconfig                    # Windows：地址、掩码、网关
route print                 # Windows：路由表
易错

“能上局域网、不能上网”最常见的原因是默认网关没配或配错，其次是 DNS 配错。先 ping 网关，再 ping 8.8.8.8，最后 ping 域名，三步就能定位。

动手练习 · 第 3 讲

  3. 一台设备 IP 是 192.168.1.10/24，网关是 192.168.2.1，能上网吗？

参考答案与思路

2. 网络地址（主机号全 0）和广播地址（全 1）不能分配给主机。

4.1知道 IP，为什么还要 MAC

IP 是“最终目的地”，MAC 是“这一跳交给谁”。数据包从主机到路由器、从路由器到下一跳，每一跳的源/目的 MAC 都会变，但源/目的 IP 不变（NAT 除外）。

4.4TTL 与分片

  • TTL：防止包在环路里永远转。每经路由器减 1，到 0 丢弃并回 ICMP Time Exceeded。

  • ICMP：网络层的“控制消息”，ping 用 Echo Request/Reply，traceroute 用 TTL 超时。

UDP、端口与套接字

UDP 不保证送达，但它没有建连、没有重传、没有队头阻塞——实时音视频和 DNS 都靠它。

5.1端口与套接字

IP 地址把数据送到主机，端口把数据送到主机上的某个程序。端口是 16 位整数（0–65535）：

范围名称说明
0–1023知名端口HTTP 80、HTTPS 443、DNS 53、MQTT 1883
1024–49151注册端口厂商/应用注册使用
49152–65535临时端口客户端发起连接时由系统分配

套接字（socket）通常指“IP + 端口 + 协议”的组合，例如 192.168.1.10:50000 TCP。一条 TCP 连接由四元组唯一确定：源 IP、源端口、目的 IP、目的端口。

5.2UDP 只做四件事

UDP 的头部只有 8 字节：源端口、目的端口、长度、校验和。它提供的能力非常有限：

提供

它做的

  • 端口复用（区分应用）
  • 可选的校验和
  • 保留消息边界（一次发 = 一个数据报）
  • 支持广播/组播
不提供

它不做的

  • 不建连、不握手
  • 不确认、不重传
  • 不保证顺序
  • 不控制拥塞
标准怎么说

IPv4 中 UDP 校验和是可选的（全 0 表示不校验），IPv6 中必须计算。校验和覆盖伪头部（源/目的 IP、协议号、UDP 长度）+ UDP 头 + 数据，所以能发现 IP 地址错误。

5.3什么时候选 UDP

场景为什么 UDP
DNS 查询一问一答，包小，重发比建连快
DHCP客户端还没有 IP，无法建 TCP；用广播

游戏状态同步只关心最新状态，旧包没价值
局域网设备发现广播/组播，TCP 不支持
CoAP / LwM2M受限设备，开销小

“UDP 不可靠”不等于“不能用”。很多协议在 UDP 之上自己做序号、确认、重传（QUIC 就是典型），把可靠性做成可定制的。

  • 拥塞控制（否则会压垮网络）。

这也是 QUIC 做的事情——它把 TCP 的可靠性 + TLS 加密搬到了 UDP 之上，避免了 TCP 的队头阻塞。

TCP：可靠字节流

TCP 把不可靠的 IP 包变成可靠的字节流。它到底保证了什么、没保证什么？为什么会有 TIME_WAIT？

学完这一讲，你能

  • 画出三次握手与四次挥手
  • 解释序号、确认、重传与滑动窗口
  • 区分流量控制与拥塞控制
  • 说明 TCP 的边界问题与粘包

6.1TCP 提供的是“字节流”，不是“消息”

TCP 保证的是：你写进去的字节，会按顺序、不重复、不丢失地到达对方。它不保留“消息边界”——你分三次写 100 字节，对方可能一次读到 300 字节，也可能分十次读到。

易错

“TCP 会粘包”是一个不准确的说法。TCP 根本没有“包”的概念，它只有字节流。所谓粘包/拆包，是应用层没有定义消息边界造成的，解决方法是长度字段、分隔符或固定长度，而不是“让 TCP 别粘”。

6.2三次握手：确认双方都能收发

步骤方向标志作用
1客户端 → 服务器SYN我想连接，我的初始序号是 x
2服务器 → 客户端SYN + ACK同意，我的初始序号是 y，确认 x+1
3客户端 → 服务器ACK确认 y+1，连接建立

为什么不是两次？两次只能确认“客户端能发、服务器能收”，无法确认“服务器能发、客户端能收”。第三次 ACK 让服务器确认自己的 SYN 被收到。

6.3序号、确认与重传

  • 序号（seq）：本段第一个字节在字节流中的位置。
  • 确认号（ack）：期望收到的下一个字节序号，表示“这之前的所有字节都收到了”（累积确认）。
  • 超时重传：发送方等不到 ACK，按 RTO 重发。RTO 根据往返时间动态估算。
  • 快速重传：收到 3 个重复 ACK，不等超时立刻重发丢失的段。
一个重传的例子text
发送方：seq=1000, len=500  → 丢失
接收方收到 seq=1500 → 回 ACK 1000
接收方收到 seq=2000 → 回 ACK 1000（重复）
接收方收到 seq=2500 → 回 ACK 1000（重复）
发送方收到 3 个重复 ACK → 立刻重发 seq=1000

6.4流量控制与拥塞控制

流量控制拥塞控制
解决什么接收方处理不过来网络中间链路拥塞
依据接收窗口 rwnd拥塞窗口 cwnd
谁决定接收方通告发送方根据丢包/延迟调整
实际发送量min(rwnd, cwnd)

拥塞控制的经典行为：慢启动（cwnd 指数增长）→ 拥塞避免（线性增长）→ 丢包时减半（AIMD）。现代算法（CUBIC、BBR）各有不同，但目标都是“尽量跑满又不压垮网络”。

6.5四次挥手与 TIME_WAIT

TCP 是全双工，两个方向要分别关闭，所以需要四次：

FIN　主动关闭方说“我没数据要发了”。
ACK　对方确认，但可能还有数据要发。
FIN　对方发完数据，也说“我发完了”。
ACK　主动关闭方确认，进入 TIME_WAIT。

TIME_WAIT 持续 2MSL（通常 60 秒），目的有两个：确保最后一个 ACK 能到达（丢了可以重发），以及让旧连接的迷路包在网络中消失，避免污染新连接。

工程习惯

服务器出现大量 TIME_WAIT 通常是“短连接太多”。可以用连接池/长连接减少，而不是简单调小 TIME_WAIT 或开 tcp_tw_reuse——后者有副作用，要理解清楚再用。

动手看

序号是“字节偏移”，不是“第几个包”。一次发送 500 字节，下一个 seq 就加 500。

7.3NAT：一个公网 IP 怎么够全家用

NAT 在路由器上改写 IP 和端口，让多台内网设备共享一个公网地址。最常见的 PAT（端口地址转换）用一个映射表：

NAT 映射表示例text
内网 192.168.1.10:50000  →  公网 203.0.113.5:40001
内网 192.168.1.11:50000  →  公网 203.0.113.5:40002

出站时改源地址/端口，回包时按表反向改写。它解决了 IPv4 地址不足，但也带来三个限制：

  • 外网不能主动连内网，除非做端口映射/打洞。
  • 映射表有超时，长时间无流量会被回收。
  • 某些协议（FTP 主动模式、SIP）在载荷里带 IP，需要 ALG 特殊处理。
工程习惯

设备作为 TCP 客户端连服务器，NAT 不是问题；设备要做“被访问的服务器”，就必须有公网映射、内网穿透或反向连接。设计物联网架构时，优先让设备主动连出（MQTT 就是这种模式）。

8.3HTTPS：HTTP over TLS

HTTPS 不是新协议，而是“HTTP 跑在 TLS 之上”。TLS 解决三件事：

机密性

对称加密（AES-GCM/ChaCha20）保护内容，中间人看不到明文。

完整性

AEAD 同时校验，篡改会被发现。

身份

证书链证明“服务器确实是它声称的那个”。

ClientHello　客户端提供支持的版本、套件、随机数、SNI。
ServerHello + 证书　服务器选套件，发送证书链。
验证证书　客户端检查签名链、有效期、域名、吊销状态。
密钥交换　TLS 1.3 用 ECDHE，一次往返完成。
Finished　双方确认握手完整性，开始加密传输。
易错

工程习惯

不要在固件里关掉证书校验来“先跑通”。这等于把 HTTPS 降级成 HTTP，中间人可以随意篡改。正确做法是内置根证书、校验证书链与域名，并保证设备时间可用（NTP 或构建时间兜底）。

8.4HTTP 客户端的常见坑

  • 没有读完响应就关闭：HTTP/1.1 复用连接时，残留数据会污染下一个请求。

MQTT：发布/订阅与 QoS

9.1MQTT 解决“很多设备、很多订阅者”

HTTP 是“客户端问、服务器答”。如果 1000 台设备都要把数据送给 10 个订阅者，HTTP 会让每台设备分别推给每个订阅者，连接数和耦合度都爆炸。

MQTT 引入 Broker：发布者只把消息发给 Broker，订阅者只从 Broker 收。双方不需要知道对方的存在，只约定主题。

标准怎么说

MQTT 是应用层协议，跑在 TCP 之上（默认 1883，TLS 为 8883）。它不是“替代 TCP/IP 的底层传输”，也不负责 IP 寻址、路由和可靠字节流——那些仍然是 TCP/IP 的工作。

9.2主题与通配符

主题示例text

home/+/temperature       + 匹配一层

9.3QoS：保证到什么程度

QoS语义交互可能的结果
0最多一次（发完就忘）PUBLISH可能丢，不会重复
1至少一次PUBLISH → PUBACK不丢，但可能重复（需要应用去重）
2恰好一次PUBLISH → PUBREC → PUBREL → PUBCOMP不丢不重，开销最大
易错

QoS 2 的“恰好一次”是在 Broker 与客户端之间的语义，不覆盖端到端业务。如果发布者重连后重发、或者业务本身重复执行，仍然可能产生重复副作用。关键操作要自己做幂等（例如带消息 ID 去重）。

11.3抓包：看到真相

当 ping 通、端口也通，但应用就是不对，就该抓包了。Wireshark 能解码 TCP 流、HTTP、MQTT，直接看到“发了什么、回了什么”。

命令行抓包（Linux / macOS）bash
sudo tcpdump -i any -n port 1883 -w mqtt.pcap
sudo tcpdump -i any -n host 192.168.1.50 and port 80
工程习惯

抓包要在两端同时抓（设备侧 + 服务器侧），才能区分“没发出去”“发出去了没收到”“收到了没处理”。只抓一端，很容易得出错误结论。

11.5综合项目：设备遥测上报

目标：设备通过 Wi-Fi 联网，周期采集数据，经 MQTT 上报；同时订阅控制主题，收到指令后执行并回复状态。全部可以在本机 + 局域网验证，不需要公网服务器。

模块职责失败时
Wi-Fi 管理连接、断线重连、信号监测指数退避重连，状态上报
MQTT 客户端连接 Broker、发布、订阅、心跳重连后重新订阅，补发离线数据
采集周期读取传感器读数非法时丢弃并计数
命令处理解析控制指令、执行、回复非法指令回复错误码
看门狗监控任务健康关键任务卡死则复位
本机验证拓扑（无需公网）text
[设备/模拟器] ──Wi-Fi/本机──> [Mosquitto Broker 192.168.1.x:1883]
                                      │
                                      ├──> [订阅者 mosquitto_sub]
                                      └──> [控制发布 mosquitto_pub]
本机启动 Broker 与订阅（示例）bash
# 安装 mosquitto 后，本机启动
mosquitto -p 1883 -v

# 另开终端：订阅所有设备遥测
mosquitto_sub -h 127.0.0.1 -t 'device/+/telemetry' -v

# 发布一条控制指令
mosquitto_pub -h 127.0.0.1 -t 'device/esp32-001/cmd' -m '{"led":1}'
实现细节

如果没有真实设备，可以用 Python 的 paho-mqtt 或 Node 的 mqtt 包写一个模拟器，行为与设备一致：连接、发布、订阅、断线重连。这样协议与后端逻辑可以先在电脑上验证，再移植到固件。

11.6验收标准

  • 设备上电后 10 秒内连上 Wi-Fi 与 Broker
  • 每 5 秒上报一次，断网后本地缓存，恢复后补发（或明确丢弃策略）
  • 收到控制指令后 1 秒内执行并回复
  • Broker 重启后设备能自动重连并重新订阅
  • 连续运行 24 小时，内存/连接数不持续增长
  • 抓包能看到完整的 CONNECT/SUBSCRIBE/PUBLISH 流程
项目练习 · 第 11 讲
  1. 用 curl -v 访问一个不存在的端口，观察错误信息。
  2. 用 tracert 看一次外网路径，指出第一跳是谁。
  3. 设计断线重连策略：初始 1 秒，最大 60 秒，指数退避 + 抖动。
  4. 如果设备时间不可用，HTTPS 证书校验会怎样？如何兜底？
参考答案与思路

1. 通常是 Connection refused，说明 IP 可达但端口没有监听。

2. 第一跳通常是家里的路由器/网关；后续是运营商网关。

3. delay = min(60, 2^n)，再加 0–1 秒随机抖动，避免所有设备同时重连造成风暴。

4. 证书有效期校验会失败（“not yet valid”）。兜底：首次联网用 NTP 校时；或使用较长有效期的证书 + 构建时间下限；不能直接关闭校验。

自测：Connection refused 通常说明？

收到 RST 才会“refused”，说明包到了对方、对方明确拒绝；完全不通通常是 timeout，DNS 失败则是名字解析错误。

本讲小结

  • ping/traceroute/netstat/curl/dig 能覆盖大部分排查。
  • 错误信息要分清 refused、timeout、DNS、TLS。
  • 抓包要两端同时抓，才能定位“哪一段丢了”。
  • 排查按链路 → 网络 → 传输 → 应用逐层进行。
  • 项目可在本机 + 局域网完整验证，不需要公网服务器。
