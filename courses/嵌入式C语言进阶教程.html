从 PC 程序到 MCU 程序

PC 程序由操作系统加载，MCU 程序上电后没人管。谁把 .data 从 Flash 搬到 RAM？谁把 .bss 清零？谁调用 main？

学完这一讲，你能

  • 说清复位后到 main 之间发生了什么
  • 区分 Flash、SRAM 与外设地址空间
  • 理解链接脚本如何决定变量放在哪
  • 知道交叉编译与 hosted / freestanding 的差别

1.1两种程序，两种“出生方式”

你在电脑上运行程序时，操作系统已经替你做了一大堆准备：分配地址空间、加载可执行文件、初始化 C 运行库、把参数传给 main。单片机上没有操作系统，上电那一刻，除了 Flash 里的机器码和一块未初始化的 SRAM，什么都没有。

同一个 main，两种运行环境
PC（hosted）MCU（freestanding）
谁加载程序操作系统复位后从固定地址取指令
谁初始化内存加载器 + C 运行库启动代码（startup）
标准库完整 libc精简版（如 newlib-nano），很多函数不可用
程序结束返回操作系统通常不允许返回，main 里是死循环
地址空间虚拟地址，由 MMU 映射物理地址，直接对应 Flash / SRAM / 外设
标准怎么说

C 标准区分 hosted 和 freestanding 两种实现。freestanding 实现只需要提供极少数头文件（<stddef.h>、<stdint.h>、<limits.h> 等），不保证有 printf、文件系统或堆。这就是为什么在单片机上用 printf 往往要重定向 _write，而且浮点格式化会显著增加 Flash 占用。

1.2从上电到 main：五步

取向量表　Cortex-M 在地址 0x00000000（或重映射后的 Flash 起始）取第一个字作为初始栈指针，第二个字作为复位入口地址。
执行 Reset_Handler　启动代码在这里运行，通常用汇编写成，还没进入 C 世界。
复制 .data　已初始化的全局/静态变量，初值存在 Flash，运行时必须复制到 SRAM，因为 SRAM 可写。
清零 .bss　未初始化（或初始化为 0）的全局/静态变量，按 C 标准必须是 0，启动代码把这块 SRAM 全部写 0。
调用 main　设置好栈之后跳进 main。很多工程的 main 末尾是 while (1)，永不返回。

1.3内存映射：地址不是“内存”，是“硬件”

在 MCU 上，地址空间是一张统一的地图：一部分地址接 Flash，一部分接 SRAM，一部分接外设寄存器。往 0x40020014 写一个数，可能不是“存起来”，而是立刻改变某个引脚的电平。

1.4链接脚本：谁决定变量住在哪

PC 上由链接器默认脚本安排地址；裸机上通常要自己写（或用厂商提供的）链接脚本。它至少描述两件事：存储器区域和段如何摆放。

link.ld · 片段（示意，非完整脚本）ld
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .text : {
        KEEP(*(.isr_vector))      /* 向量表必须放在最前面 */
        *(.text*)
        *(.rodata*)
    } > FLASH

    .data : {
        *(.data*)
    } > RAM AT > FLASH           /* 运行在 RAM，初值存在 FLASH */

    .bss : {
        *(.bss*)
        *(COMMON)
    } > RAM
}
实现细节

> RAM AT > FLASH 是理解启动代码的关键：.data 段的运行地址在 RAM，加载地址在 Flash。启动代码要按这两个地址把初值搬过去。搬多少、从哪搬，由链接器生成的符号（如 _sdata、_edata、_sidata）告诉启动代码。

1.5交叉编译：在 x86 上生成 ARM 代码

你的电脑是 x86-64，目标板是 ARM Cortex-M。编译器本身跑在 x86 上，但生成的是 ARM 指令，这叫交叉编译。工具链前缀通常写明目标，例如 arm-none-eabi-gcc。

终端（示例：Cortex-M4）bash
arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=c11 \
  -Wall -Wextra -O2 -g \
  -ffunction-sections -fdata-sections \
  -T link.ld -nostartfiles \
  main.c startup.c -o app.elf

arm-none-eabi-size app.elf        # 看 text / data / bss 占用
arm-none-eabi-objdump -h app.elf  # 看各段地址与大小
选项作用
-mcpu= / -mthumb指定内核与指令集；选错会直接跑飞
-nostartfiles不使用工具链默认启动文件，改用工程自己的 startup
-T link.ld指定链接脚本
-ffunction-sections -fdata-sections每个函数/变量单独成段，配合 --gc-sections 删除未用代码
-specs=nano.specs使用 newlib-nano，显著减小 Flash 占用（GCC 工具链）
-Wl,-Map=app.map生成映射文件，查符号地址和空间占用

1.6一个最小裸机程序的骨架

main.c · 平台相关（Cortex-M 示例）C11
#include <stdint.h>

/* 这两个符号由链接脚本提供，声明成外部符号即可使用 */
extern uint32_t _sdata, _edata, _sidata;
extern uint32_t _sbss, _ebss;

int main(void);          /* 由应用提供，启动代码只负责调用 */

void Reset_Handler(void)
{
    /* 1. 复制 .data：从 Flash 的加载地址搬到 RAM */
    uint32_t *src = &_sidata;
    for (uint32_t *dst = &_sdata; dst < &_edata; ) {
        *dst++ = *src++;
    }

    /* 2. 清零 .bss */
    for (uint32_t *dst = &_sbss; dst < &_ebss; ) {
        *dst++ = 0;
    }

    /* 3. 进入 C 世界 */
    main();

    for (;;) { }        /* main 不允许返回 */
}
工程习惯

实际工程里这段通常由厂商提供的 startup_*.s 完成，还会初始化时钟、FPU、看门狗。你不需要背汇编，但必须知道它做了哪几件事——否则“全局变量初值不对”“未初始化变量不是 0”这类问题会很难查。

参考答案与思路

2. RAM 掉电丢失，烧录器只能把数据写进非易失的 Flash；运行时才把初值复制到 RAM，因为变量需要可写。

3. 所有未显式初始化的全局/静态变量，以及显式初始化为 0 的变量。C 标准保证它们是 0；如果没清零，它们会是上电后的随机值（或上一次复位前的残留）。

4. text 是代码和常量，放 Flash；data 是已初始化且非 0 的全局/静态变量，运行时占 RAM（初值占 Flash）；bss 是零初始化变量，只占 RAM，不占 Flash 镜像。

自测：启动代码必须把 .data 段从 Flash 复制到 RAM，根本原因是？

全局变量的初值必须保存在非易失存储器里（否则掉电就没了），但程序运行时要能修改它们，所以只能把初值放在 Flash，启动时复制到 RAM。

寄存器与内存映射 I/O

“配置一个引脚”本质上就是往某个固定地址写几个位。理解内存映射，寄存器就不再是魔法数字。

学完这一讲，你能

  • 用地址访问外设寄存器并解释 volatile 的必要性
  • 区分置位、清位、翻转与读改写
  • 说明为什么读改写可能丢失中断里的修改
  • 认识厂商头文件与 CMSIS 的组织方式

2.1寄存器就是一个固定地址

“配置 GPIO”听起来抽象，落到代码上只有一句话：往某个固定地址写一个特定宽度的值。芯片手册给出的寄存器表，本质上是一张“地址 + 位定义”的说明书。

reg_raw.c · 平台相关（地址为 STM32 示例）C11
#include <stdint.h>

#define GPIOA_BASE   0x40020000UL
#define GPIOA_MODER  (*(volatile uint32_t *)(GPIOA_BASE + 0x00UL))
#define GPIOA_ODR    (*(volatile uint32_t *)(GPIOA_BASE + 0x14UL))

void led_init(void)
{
    /* 把 PA5 配置为通用输出：MODER[11:10] = 01 */
    GPIOA_MODER &= ~(3UL << 10);      /* 先清两位 */
    GPIOA_MODER |=  (1UL << 10);      /* 再写 01 */

    GPIOA_ODR |= (1UL << 5);          /* 输出高电平 */
}

拆开看这个宏：

  • 0x40020000UL 是整数常量，UL 保证它是 unsigned long，避免在 16 位 int 的平台上溢出。
  • (volatile uint32_t *) 把整数转换成“指向 32 位寄存器的指针”。
  • 外面的 * 解引用，于是 GPIOA_MODER 可以像普通变量一样赋值——但每次访问都会真的读写那个地址。
标准怎么说

把整数转成指针、再解引用一个“不是 C 对象”的地址，严格来说超出了 C 标准描述的范围（标准只保证对象和数组内部的指针算术）。这是实现定义 + 平台约定：编译器明确支持内存映射 I/O，芯片手册保证该地址有效。写驱动时必须同时信任这两份文档。

2.2volatile：让编译器“每次都真的去读”

没有 volatile 时，编译器可以合理地假设“这个变量的值不会自己变”，于是把多次读取合并成一次，甚至把整个循环优化掉。

volatile_demo.cC11
/* 错误：编译器可能只读一次 STATUS，然后死循环 */
while (STATUS == 0) { }

/* 正确：每次都从地址重新读取 */
while (*(volatile uint32_t *)STATUS_ADDR == 0) { }

volatile 告诉编译器三件事：

不能省

每次访问都必须真实发生，不能合并、不能缓存到寄存器。

不能重排

同一线程内，volatile 访问之间的顺序不会被编译器调换。

仅此而已

它不保证原子性，不保证多核之间的可见性，也不是锁。

易错

“用 volatile 就能在多任务/中断里安全共享变量”是错误结论。volatile 只解决“编译器优化掉访问”，不解决“读到一半被中断打断”。第 11 讲会专门处理这个问题。

2.3厂商头文件为什么那样写

真实工程不会为每个寄存器写一个宏，而是用结构体把一组寄存器连续排列，再用基地址转成指针：

reg_struct.c · 平台相关（布局为示例）C11
#include <stdint.h>

typedef struct {
    volatile uint32_t MODER;     /* 0x00 */
    volatile uint32_t OTYPER;    /* 0x04 */
    volatile uint32_t OSPEEDR;   /* 0x08 */
    volatile uint32_t PUPDR;     /* 0x0C */
    volatile uint32_t IDR;       /* 0x10 */
    volatile uint32_t ODR;       /* 0x14 */
    volatile uint32_t BSRR;      /* 0x18 */
    volatile uint32_t LCKR;      /* 0x1C */
    volatile uint32_t AFR[2];    /* 0x20, 0x24 */
} GPIO_TypeDef;

#define GPIOA ((GPIO_TypeDef *)0x40020000UL)

void led_on(void)
{
    GPIOA->BSRR = (1UL << 5);    /* 写 1 置位，单次写，天然原子 */
}

这种写法依赖两个前提：结构体成员之间没有填充，且每个成员都是 4 字节。只要成员全是 uint32_t，在常见 ABI 下就成立；一旦混入 uint8_t，就可能出现填充，寄存器偏移全错。厂商头文件通常会用编译期断言检查偏移。

实现细节

CMSIS 把这种结构体指针封装成 GPIOA 这样的宏，并加上 __IO（即 volatile）修饰。不同厂商命名不同，但套路一致：基地址 + 结构体偏移 + volatile。

2.4读改写：一行 C 其实是三步

REG |= (1 << 3); 看起来是一个动作，编译后通常是：

读　把 REG 的 32 位值从外设读进 CPU 寄存器。
改　在 CPU 里做按位或。
写　把结果写回 REG。

如果在这三步之间来了中断，而中断也修改了同一个寄存器，那么中断的修改会被主流程的“写回”覆盖——这叫读改写丢失更新。

rmw_race.c · 片段C11
/* 主循环 */
REG |= (1u << 3);

/* 中断里 */
REG |= (1u << 7);

/* 可能的执行顺序：
   主：读 REG（bit7=0）
   中断：读 REG（bit7=0），写回 bit7=1
   主：写回自己算出的值（bit7 仍是 0）→ 中断的修改丢了
*/
正确做法

优先使用硬件提供的原子置位/清位寄存器（例如 STM32 的 BSRR：写 1 置位、写 0 无影响；写 1 到高 16 位清位）。没有这种寄存器时，用临界区保护整段读改写，或者用位带（如果芯片支持）。

2.5写 1 清除：不能想当然

有些状态寄存器的语义是“写 1 清除”（write-1-to-clear）。这时 REG &= ~(1 << n) 不但清不掉，还可能把其他位清掉，因为写 0 在该位上“无动作”，而其他位写 0 也可能触发清除。

w1c.c · 片段C11
/* 假设 bit0..bit3 都是 write-1-to-clear 的标志位 */
REG = (1u << 2);        /* 只清 bit2：直接赋值，不要读改写 */
工程习惯

读寄存器手册时，先确认每个字段的访问类型：RW、RO、W1C、RC_W0……访问类型比位定义更容易被忽略，也更容易导致“明明写了却没效果”。

  3. 结构体映射寄存器时，如果中间插入一个 uint8_t 成员，会发生什么？
  4. 什么情况下必须用临界区保护读改写？
参考答案与思路

1. REG = (REG & ~(0xFUL << 12)) | (0xAUL << 12);。先清 4 位，再写入目标值。

2. 非 volatile 时编译器可以把 REG 读一次存到寄存器，循环条件不再重新读内存；如果初值为 0，就永远不结束；如果编译器认为循环无副作用，还可能整个删掉。

3. 编译器会在 uint8_t 后插入填充，使下一个 uint32_t 对齐到 4 字节，后续所有寄存器偏移都错位。

4. 当同一寄存器会被主循环和中断（或两个任务）同时读改写，且硬件没有原子置位/清位寄存器时。

自测：volatile 能保证下面哪一项？

volatile 只约束编译器，不提供原子性，也不提供内存屏障语义（跨核/跨设备的顺序需要额外手段）。原子性要靠硬件指令、临界区或 C11 原子类型。

3.2字段的三个动作：读、写、改

field_ops.c · 片段C11
/* 读：先右移对齐，再与掩码 */
static inline uint32_t field_get(uint32_t reg, uint32_t pos, uint32_t msk)
{
    return (reg & msk) >> pos;
}

/* 写：先清掉字段，再放入新值（调用者保证 value 不超宽） */
static inline uint32_t field_set(uint32_t reg, uint32_t pos, uint32_t msk, uint32_t value)
{
    return (reg & ~msk) | ((value << pos) & msk);
}

/* 用宏也可以，但内联函数有类型检查，调试也友好 */
#define FIELD_GET(reg, msk, pos)   (((reg) & (msk)) >> (pos))
#define FIELD_SET(reg, msk, pos, v) (((reg) & ~(msk)) | (((v) << (pos)) & (msk)))
易错

(value << pos) & msk 里的 & msk 不是可有可无的：如果 value 超出字段宽度，不移除高位就会污染相邻字段。反过来，如果调用者已经保证不超宽，这个与运算也能防止手误。

3.4四个高频位技巧

bit_tricks.cC11
#include <stdint.h>
#include <stdbool.h>

/* 1. 判断是不是 2 的幂（0 不是） */
bool is_pow2(uint32_t x) { return x != 0u && (x & (x - 1u)) == 0u; }

/* 2. 统计 1 的个数（Brian Kernighan 法） */
int popcount(uint32_t x)
{
    int n = 0;
    while (x) { x &= (x - 1u); n++; }
    return n;
}

/* 3. 取出最低的 1 及其位置 */
uint32_t lowest_bit(uint32_t x) { return x & (~x + 1u); }   /* x & -x */

/* 4. 循环右移（避免负数右移的实现定义行为） */
uint32_t ror(uint32_t x, unsigned n)
{
    n &= 31u;
    return n ? (x >> n) | (x << (32u - n)) : x;
}
标准怎么说

对无符号类型，左移和右移都是良定义的（左移按 2N 取模，右移是逻辑右移）。对有符号负数右移，结果是实现定义；对有符号数左移到符号位，是未定义行为。写底层代码时，位运算一律用无符号类型。

const、volatile、static、extern

这四个关键字几乎每个嵌入式面试都会问，但最常见的答案是错的：volatile 不是原子操作，const 也不保证放进 Flash。

学完这一讲，你能

  • 准确说明 volatile 保证什么、不保证什么
  • 区分 static 的三种含义
  • 正确使用 extern 声明跨文件变量
  • 解释 const 与只读存储没有必然关系

4.1const：一个承诺，不是一种存储

const 的含义是“通过这个名字不能修改”。它不保证对象真的存放在只读存储器里，也不保证别人不能改。

const_semantics.cC11
const int table[4] = {1, 2, 3, 4};
/* table[0] = 9;   编译错误：通过 table 不能改 */

int *p = (int *)table;   /* 强制去掉 const：语法上能过 */
/* *p = 9;              未定义行为：修改 const 对象 */

const int n = 10;
int arr[n];              /* C99 VLA；不是“常量表达式”，不能用于 case 标签 */
常见说法是否准确更准确的说法
const 变量一定在 Flash / ROM不准确可能被放进 .rodata，也可能被优化成立即数，甚至放在栈上；由实现和链接脚本决定。
const 变量不能改部分准确不能通过这个名字改；通过强制转换后的指针修改是未定义行为。
const 可以用来做数组长度不准确C 里 const int 不是整型常量表达式；用 #define 或 enum。
函数参数加 const 更安全准确它表达“我不会改你的数据”，是接口契约的一部分。
工程习惯

只读查表数据（如字库、CRC 表、字符串）写 const，让链接器有机会放进 Flash，节省宝贵的 SRAM。但不要假设“写了 const 就一定省 RAM”，要看 map 文件确认。

4.2volatile：三保证，三不保证

保证

它确实做的

  • 每次访问都真实发生，不合并、不缓存
  • 不会被优化删除
  • 同一线程内，volatile 访问的相对顺序不被编译器调换
不保证

它做不到的

  • 不保证原子性（32 位写可能分成两次 16 位）
  • 不保证多核/多设备的可见性与顺序（需要屏障或原子类型）
  • 不替代锁，不解决竞态
volatile_use.cC11
#include <stdint.h>
#include <stdbool.h>

/* 1. 内存映射寄存器：必须 volatile */
#define STATUS (*(volatile uint32_t *)0x40001000UL)

/* 2. 中断与主循环共享的标志：必须 volatile */
volatile bool g_button_pressed = false;

void EXTI_IRQHandler(void)
{
    g_button_pressed = true;      /* 中断里写 */
}

int main(void)
{
    while (1) {
        if (g_button_pressed) {   /* 主循环读：没有 volatile 可能被优化成只读一次 */
            g_button_pressed = false;
            /* 处理按键 */
        }
    }
}

/* 3. 只读状态寄存器：const + volatile 组合 */
#define ID_REG (*(const volatile uint32_t *)0x40001FF0UL)
易错

下面这段代码即使加了 volatile 也不安全：

counter_race.c · 片段C11
volatile uint32_t counter = 0;
counter++;      /* 读-改-写三步，中断可能插在中间 */

两个上下文同时执行 counter++，可能各自读到 5，各自写回 6，最终少加一次。正确做法是关中断做临界区，或用硬件原子指令，或使用 C11 _Atomic。

4.3static：一个关键字，三种身份

位置含义典型用途
函数内部的变量静态存储期：只初始化一次，函数返回后仍存在计数器、状态缓存、一次性初始化标志
文件作用域的变量/函数内部链接：其他 .c 文件看不到模块私有实现，避免符号冲突
数组参数中的 staticC99：承诺至少能访问这么多元素给编译器优化提示，日常很少用

static int module_counter;              /* 只在本文件可见 */

void api_init(void)
{
    static bool inited = false;         /* 只初始化一次 */

实现细节

函数内的 static 变量如果没有显式初始化，会被清零，且初始化发生在程序启动前（对嵌入式来说就是启动代码的清零/复制阶段）。它不是线程安全的：多个任务同时第一次调用，可能都看到 inited == false。

4.4extern：声明“别处有定义”

module.hC11

#define MODULE_H

/* 定义：真正分配存储，整个程序只能有一处 */

常见错误是在头文件里写 uint32_t g_sample_count = 0;：每个包含它的 .c 都会生成一份定义，链接时报 multiple definition。

标准怎么说

在 C 中，文件作用域的 int x; 是暂定定义（tentative definition），同一个翻译单元里可以出现多次，最终合并为一个；但跨翻译单元仍然是多个定义。extern int x; 是纯声明，不分配存储。C++ 的规则不同，不要把 C++ 的 inline 变量习惯带过来。

在 8 位机上，int 可能是 16 位；一个 uint8_t 相加就可能溢出。跨平台代码不能靠“我这台机器没问题”。

5.1“int 是 4 字节”只是一个巧合

C 标准只规定最小范围，不规定字节数：int 至少 16 位，long 至少 32 位，long long 至少 64 位。在 8 位 MCU 上，int 常常就是 16 位；某些 DSP 上 char 甚至不是 8 位。

width_check.cC11
#include <limits.h>
#include <stdio.h>

int main(void)
{
    printf("CHAR_BIT = %d\n", CHAR_BIT);
    printf("int      = %d 位\n", (int)(sizeof(int) * CHAR_BIT));
    printf("INT_MAX  = %d\n", INT_MAX);
    printf("long     = %d 位\n", (int)(sizeof(long) * CHAR_BIT));
    return 0;
}
运行结果
CHAR_BIT = 8
int      = 32 位
INT_MAX  = 2147483647
long     = 32 位

这段输出来自 64 位 Windows（LLP64）：long 仍是 32 位。在 64 位 Linux 上会是 64 位。所以“用 long 存指针”这类写法从一开始就不可移植。

8 位值扩展成 32 位

输入一个 8 位十六进制值，对比“按有符号扩展”和“按无符号零扩展”的结果。

这正是 int8_t 与 uint8_t 在表达式里表现不同的根源。

5.4移位的四条规则

shift_rules.c · 片段C11
uint32_t u = 1u;

u << 31;        /* 合法：无符号左移，按 2^32 取模 */
u << 32;        /* 未定义行为：移位位数 >= 类型宽度 */

int32_t s = -1;
s << 1;         /* 未定义行为：左移负数 */
s >> 1;         /* 实现定义：可能是算术右移（-1），也可能是逻辑右移 */

uint32_t x = 0x80000000u;
x >> 1;         /* 合法：逻辑右移，得到 0x40000000 */
工程习惯

需要“算术右移”时，不要依赖 >> 对有符号数的行为。可以显式写：(x >> n) | (~((x >> n) | ~(x >> n)) ...)——太绕了。更实际的做法是：确认目标编译器的行为并写进移植说明，或者先把有符号数转成无符号处理位模式。

5.5字节序：内存里的顺序

一个 32 位整数 0x12345678 在内存里可以有两种排法：

小端

低字节在前

78 56 34 12。x86、大多数 ARM（可配置）、RISC-V 默认小端。

大端

高字节在前

12 34 56 78。部分网络协议、某些 DSP 和 PowerPC 使用大端。

endian.cC11
#include <stdint.h>
#include <stdio.h>

uint32_t swap32(uint32_t v)
{
    return ((v & 0x000000FFu) << 24) |
           ((v & 0x0000FF00u) << 8)  |
           ((v & 0x00FF0000u) >> 8)  |
           ((v & 0xFF000000u) >> 24);
}

int main(void)
{
    uint32_t v = 0x12345678u;
    printf("%08X -> %08X\n", v, swap32(v));
    return 0;
}
运行结果
12345678 -> 78563412
易错

把 uint8_t buf[4] 直接用 memcpy 到 uint32_t，得到的值取决于本机字节序。协议里规定“大端传输”时，必须显式按字节组装，不能依赖 memcpy。

be_read.cC11
#include <stdint.h>

/* 从大端字节流读取 32 位，与主机字节序无关 */
uint32_t read_be32(const uint8_t *p)
{
    return ((uint32_t)p[0] << 24) |
           ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8)  |
           ((uint32_t)p[3]);
}

5.6三个真实踩过的坑

int_traps.cC11
#include <stdint.h>

/* 坑 1：两个 uint8_t 相加，结果是 int，不是 uint8_t */
uint8_t a = 200, b = 100;
uint8_t c = a + b;            /* 300 截断成 44 */

/* 坑 2：char 是否有符号由实现决定 */
char ch = 0xFF;
int v = ch;                   /* 可能是 255，也可能是 -1 */

/* 坑 3：有符号与无符号比较 */
int32_t  i = -1;
uint32_t u = 1;
if (i < u) { }                /* 假：i 被转成 4294967295 */
正确做法

处理字节数据一律用 uint8_t；需要字符语义时用 char，但不要假设它的符号性；比较前统一类型，或显式转换并确认范围。

6.1变量到底落在哪一段

写法段占用说明
int g = 1;.dataFlash 存初值 + RAM 占 4 字节已初始化且非 0
int g; 或 int g = 0;.bss只占 RAM启动时清零，不占 Flash 镜像
const int t[] = {...};.rodata（通常）Flash是否真的不占 RAM 要看链接脚本

malloc(n)堆RAM嵌入式里常被禁用或限制大小

在资源紧张的 MCU 上，“这个变量占不占 RAM”比“它是什么类型”更重要。一张 1 KB 的 const 表如果被放进 .data，就会白白吃掉 1 KB SRAM。

6.2对齐规则：三条就够

成员对齐　每个成员的偏移必须是它自身对齐要求的整数倍。例如 int 要求 4 字节对齐，偏移只能是 0、4、8……
结构体对齐　结构体整体的对齐等于所有成员中最大的对齐要求。
末尾补齐　结构体总大小必须是整体对齐的整数倍，以便数组中相邻元素仍然对齐。
layout.cC11
#include <stdio.h>
#include <stddef.h>

struct A {
    char  a;     /* 偏移 0，占 1 字节 */
                 /* 3 字节填充 */
    int   b;     /* 偏移 4 */
    short c;     /* 偏移 8 */
                 /* 2 字节填充（总大小要是 4 的倍数） */
};

struct B {
    int   b;     /* 0 */
    short c;     /* 4 */
    char  a;     /* 6 */
                 /* 1 字节填充 */
};

int main(void)
{
    printf("A: size=%zu  a=%zu b=%zu c=%zu\n",
           sizeof(struct A), offsetof(struct A, a), offsetof(struct A, b), offsetof(struct A, c));
    printf("B: size=%zu  b=%zu c=%zu a=%zu\n",
           sizeof(struct B), offsetof(struct B, b), offsetof(struct B, c), offsetof(struct B, a));
    return 0;
}
运行结果
A: size=12  a=0 b=4 c=8
B: size=8  b=0 c=4 a=6

同样的三个成员，只是换了顺序，大小从 12 变成 8。把大的成员放前面，通常能减少填充——这是嵌入式里很实用的一个小技巧。

结构体布局计算器

紧凑布局用 __attribute__((packed)) 或 #pragma pack(1) 实现，代价是成员可能落在非对齐地址上。

6.3紧凑布局：省了空间，付出了什么

packed.c · 平台相关（GCC/Clang 扩展）C11
struct __attribute__((packed)) Frame {
    uint8_t  type;      /* 0 */
    uint32_t value;     /* 1，未对齐 */
    uint16_t crc;       /* 5，未对齐 */
};                      /* sizeof = 7 */
代价说明
访问变慢编译器要把一次 32 位访问拆成多次字节访问再拼起来。
可能硬件异常Cortex-M0、部分 RISC-V 配置不支持非对齐访问，直接 HardFault。
不能取成员地址当普通指针&frame.value 是“可能未对齐的指针”，解引用是未定义行为。
标准之外packed 是编译器扩展，不是 C 标准语法。
工程习惯

解析协议时，推荐“按字节读 + 显式组装”，而不是把接收缓冲区强制转换成 packed 结构体。前者可移植、可测试，也不受对齐影响：

uint32_t value = ((uint32_t)buf[1] << 24) | ((uint32_t)buf[2] << 16) |
                 ((uint32_t)buf[3] << 8)  |  (uint32_t)buf[4];

6.4结构体不是字节流

下面这段代码在本机可能“能用”，换平台就错：

send_struct.c · 错误示范C11
struct Reading { uint16_t id; float value; };
struct Reading r = {1, 23.5f};

send(fd, &r, sizeof r);      /* 三个问题 */
  • 填充：id 后可能有 2 字节填充，内容不确定，会一起发出去。
  • 字节序：id 和 float 的字节顺序取决于发送方。
  • 浮点格式：IEEE 754 是事实标准，但并非所有平台都相同；对齐和大小也可能不同。
serialize.cC11
#include <stdint.h>
#include <string.h>

/* 明确的线格式：大端，id 2 字节 + value 4 字节 IEEE754 */
void encode_reading(uint8_t out[6], uint16_t id, float value)
{
    uint32_t bits;
    memcpy(&bits, &value, sizeof bits);       /* 取浮点的位模式 */

    out[0] = (uint8_t)(id >> 8);
    out[1] = (uint8_t)(id);
    out[2] = (uint8_t)(bits >> 24);
    out[3] = (uint8_t)(bits >> 16);
    out[4] = (uint8_t)(bits >> 8);
    out[5] = (uint8_t)(bits);
}
标准怎么说

标准只保证结构体成员的顺序与声明一致，不保证没有填充，也不规定填充的内容。把结构体按字节发送，等于把“本平台的布局细节”泄露到协议里。

6.5用 offsetof 和断言锁住布局

layout_assert.cC11
#include <stddef.h>
#include <stdint.h>

struct Header {
    uint8_t  version;
    uint8_t  type;
    uint16_t length;
    uint32_t seq;
};

/* 如果编译器插入了意料之外的填充，这里会编译失败 */
_Static_assert(offsetof(struct Header, length) == 2, "length 必须在偏移 2");
_Static_assert(offsetof(struct Header, seq) == 4, "seq 必须在偏移 4");
_Static_assert(sizeof(struct Header) == 8, "Header 必须是 8 字节");

这类断言在跨平台工程里价值极高：它把“我以为的布局”变成“编译器必须接受的布局”。一旦换芯片或换编译器导致布局变化，编译期就会报错，而不是等到通信对不上。

7.1指针复习：这次关注“指向什么”

第 1 册讲过：指针存地址，类型决定步长和解引用宽度。到了嵌入式，指针多了一个新任务——指向代码。函数在内存里也有地址，也可以被指针指向。

func_ptr_basic.cC11
#include <stdio.h>

int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

int main(void)
{
    int (*op)(int, int) = add;     /* 函数指针：参数和返回值必须匹配 */
    printf("%d\n", op(3, 4));      /* 7 */

    op = sub;                      /* 指向另一个函数 */
    printf("%d\n", op(3, 4));      /* -1 */

    printf("%d\n", (*op)(3, 4));   /* 也可以显式解引用，等价 */
    return 0;
}
运行结果
7
-1
-1
标准怎么说

函数名在表达式中会转换成“指向函数的指针”（除 sizeof 和 & 外）。所以 op = add 和 op = &add 等价，op(3,4) 和 (*op)(3,4) 也等价。两种写法都对，选一种统一即可。

7.4不透明指针：把实现藏起来

sensor.hC11
#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

/* 只声明，不定义：调用者无法知道结构体里有什么 */
typedef struct sensor sensor_t;

sensor_t *sensor_create(uint8_t bus, uint8_t addr);
void      sensor_destroy(sensor_t *s);
int       sensor_read(sensor_t *s, int32_t *out);

#endif
sensor.cC11
#include "sensor.h"
#include <stdlib.h>

struct sensor {
    uint8_t bus;
    uint8_t addr;
    int32_t last;
};

sensor_t *sensor_create(uint8_t bus, uint8_t addr)
{
    sensor_t *s = malloc(sizeof *s);
    if (s == NULL) {
        return NULL;
    }
    s->bus = bus;
    s->addr = addr;
    s->last = 0;
    return s;
}

void sensor_destroy(sensor_t *s) { free(s); }

int sensor_read(sensor_t *s, int32_t *out)
{
    if (s == NULL || out == NULL) {
        return -1;
    }
    *out = s->last;      /* 真实实现会去读硬件 */
    return 0;
}

这种设计叫不透明指针（opaque pointer）。调用者只能通过 sensor_* 函数操作对象，无法直接改字段。好处是：实现可以随时改，ABI 稳定；坏处是多了一次堆分配，且调用者必须记得 destroy。

工程习惯

资源受限时，可以用“静态对象池 + 句柄”替代 malloc：sensor_create 从固定数组里取一个槽位，返回索引或指针。这样既有封装，又不依赖堆。

7.5签名不匹配：编译器不一定救你

wrong_cb.c · 片段C11
void my_cb(int code);                 /* 只有一个参数 */

/* 期望 void (*)(uart_event_t, void *) */
uart_listener_t l = { (uart_cb_t)my_cb, NULL };   /* 强制转换：编译器闭嘴了 */

强制转换函数指针可以绕过类型检查，但调用时的参数传递方式由真实签名决定。参数个数或类型不一致，行为未定义——在 x86 上可能“碰巧能跑”，在 ARM 上可能直接跑飞。

易错

不要把函数指针转成 void * 再转回来。ISO C 不保证函数指针能放进对象指针；POSIX 才要求两者大小相同。需要泛型回调时，用 void (*)(void *) 这种明确的签名，而不是硬转。

8.1为什么驱动要分层

状态机与事件驱动

按键、协议解析、设备流程，本质都是状态机。写成一堆 if-else，三个月后自己都看不懂。

学完这一讲，你能

  • 用 enum + switch 写出清晰的状态机

  • 用表驱动替代长 switch

9.1什么时候该用状态机

当一段逻辑满足下面任意两条，就该考虑状态机：

  • 行为依赖“之前发生过什么”，而不是只看当前输入。
  • 分支里出现多层嵌套的 if，且每层都在判断“现在处于哪个阶段”。
  • 需要处理超时、重试、异常恢复。
  • 同一件事在不同阶段有不同反应（例如“连接中”收到数据要丢弃，“已连接”收到数据要处理）。

状态机把这些隐含的“阶段”显式写出来：状态是现在在哪，事件是发生了什么，迁移是接下来去哪，动作是迁移时做什么。

9.2用 enum + switch 写一个

fsm_switch.cC11
#include <stdint.h>
#include <stdio.h>

typedef enum {
    ST_IDLE = 0,
    ST_CONNECTING,
    ST_READY,
    ST_ERROR
} state_t;

typedef enum {
    EV_START = 0,
    EV_CONNECTED,
    EV_TIMEOUT,
    EV_FAIL,
    EV_RESET
} event_t;

typedef struct {
    state_t  state;
    uint32_t retry;
} fsm_t;

static void on_enter(state_t s)
{
    printf("  -> 进入状态 %d\n", (int)s);
}

void fsm_dispatch(fsm_t *f, event_t ev)
{
    switch (f->state) {
    case ST_IDLE:
        if (ev == EV_START) {
            f->state = ST_CONNECTING;
            on_enter(f->state);
        }
        break;

    case ST_CONNECTING:
        if (ev == EV_CONNECTED) {
            f->state = ST_READY;
            f->retry = 0;
            on_enter(f->state);
        } else if (ev == EV_TIMEOUT || ev == EV_FAIL) {
            f->retry++;
            if (f->retry >= 3) {
                f->state = ST_ERROR;
                on_enter(f->state);
            }
            /* 否则留在 CONNECTING，等待下一次重试 */
        }
        break;

    case ST_READY:
        if (ev == EV_FAIL || ev == EV_TIMEOUT) {
            f->state = ST_CONNECTING;
            on_enter(f->state);
        }
        break;

    case ST_ERROR:
        if (ev == EV_RESET) {
            f->state = ST_IDLE;
            f->retry = 0;
            on_enter(f->state);
        }
        break;

    default:
        f->state = ST_ERROR;
        break;
    }
}
工程习惯

每个 switch 都写 default，把非法状态收敛到 ST_ERROR。状态变量被内存踩坏时，程序会进入可控的故障态，而不是执行随机的分支。

9.3表驱动：状态多了以后

fsm_table.cC11
#include <stddef.h>

typedef void (*action_fn)(fsm_t *f);

typedef struct {
    state_t   from;
    event_t   event;
    state_t   to;
    action_fn action;
} transition_t;

static void act_start(fsm_t *f)   { (void)f; }
static void act_fail(fsm_t *f)    { f->retry++; }

static const transition_t g_table[] = {
    { ST_IDLE,       EV_START,     ST_CONNECTING, act_start },
    { ST_CONNECTING, EV_CONNECTED, ST_READY,      NULL      },
    { ST_CONNECTING, EV_FAIL,      ST_ERROR,      act_fail  },
    { ST_ERROR,      EV_RESET,     ST_IDLE,       NULL      },
};

void fsm_dispatch_table(fsm_t *f, event_t ev)
{
    for (size_t i = 0; i < sizeof g_table / sizeof g_table[0]; i++) {
        if (g_table[i].from == f->state && g_table[i].event == ev) {
            if (g_table[i].action != NULL) {
                g_table[i].action(f);
            }
            f->state = g_table[i].to;
            return;
        }
    }
    /* 没有匹配的迁移：记录日志或进入错误态 */
}

9.4非阻塞：状态机的好搭档

状态机让“等”变成“记住现在在等”。不要在状态处理里写 delay_ms(1000)，而是记录时间戳，下次进来检查是否超时。

fsm_timeout.cC11
#include <stdint.h>
#include <stdbool.h>

typedef struct {
    state_t  state;
    uint32_t deadline_ms;
} conn_t;

/* 由 1 ms 定时器或主循环周期调用 */
void conn_tick(conn_t *c, uint32_t now_ms)
{
    if (c->state == ST_CONNECTING && (int32_t)(now_ms - c->deadline_ms) >= 0) {
        fsm_dispatch((fsm_t *)c, EV_TIMEOUT);   /* 超时，走重试逻辑 */
        c->deadline_ms = now_ms + 500;          /* 下一次超时时间 */
    }
}
实现细节

(int32_t)(now - deadline) >= 0 是处理计时器回绕的标准写法：无符号相减得到差值，转成有符号再比较，即使 now 溢出也能正确判断。直接写 now >= deadline 在回绕时会出错。

环形缓冲区与数据解析

串口数据随时会来，CPU 不能等。环形缓冲区用一块固定内存，把“生产者”和“消费者”解耦。

10.1为什么是“环形”

串口数据随时可能到达，CPU 不能停下来等。最直接的做法是开一个大数组，来一个字节存一个——但数组总会满，满了就要搬移数据，搬移又要时间。

环形缓冲区（ring buffer / FIFO）用固定大小的数组 + 两个指针解决这个问题：写指针向前走，走到末尾就回到开头；读指针同理。不需要搬移，插入和取出都是 O(1)。

10.2怎么区分“满”和“空”

如果只有 head 和 tail，那么 head == tail 既可能是空，也可能是满。三种常见解法：

方案做法容量代价
浪费一个槽位(head + 1) % N == tail 判满N-1少存一个元素，逻辑最简单
额外计数维护 count，0 为空、N 为满N多一个变量，读写都要更新

{
    r->head = 0;
    r->tail = 0;
}

{

}

{
    return (uint16_t)((r->head + 1u) % RING_CAP) == r->tail;
}

{
    return (size_t)((r->head + RING_CAP - r->tail) % RING_CAP);
}

bool ring_push(ring_t *r, uint8_t byte)
{
    uint16_t next = (uint16_t)((r->head + 1u) % RING_CAP);
    if (next == r->tail) {
        return false;                 /* 满：丢弃或由调用者处理 */
    }
    r->buf[r->head] = byte;
    r->head = next;                   /* 先写数据，再移动指针 */
    return true;
}

bool ring_pop(ring_t *r, uint8_t *out)
{
    if (r->head == r->tail) {
        return false;                 /* 空 */
    }
    *out = r->buf[r->tail];
    r->tail = (uint16_t)((r->tail + 1u) % RING_CAP);
    return true;
}
工程习惯

“先写数据，再移动 head”是单生产者单消费者场景下的关键顺序：消费者看到 head 前进时，数据一定已经写好了。反过来（先动指针再写数据）会让消费者读到旧值。更严格的多核场景还需要内存屏障。

10.3字节流不是消息流

串口给你的是连续的字节。一次中断可能收到半个帧，也可能收到一帧半。解析器必须自己解决三件事：

粘连

两次数据粘在一起：[帧1][帧2]。必须按长度切开，不能假设“一次读 = 一帧”。

分片

一帧分几次到达：[帧头+长度] 然后 [载荷]。必须缓存中间状态。

噪声

总线上出现乱码。必须能重新同步到帧头，而不是一直错位。

10.4解析状态机

parser.cC11
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

#define SOF       0xA5u
#define MAX_PAYLOAD 32u

typedef enum {
    PS_WAIT_SOF = 0,
    PS_WAIT_LEN,
    PS_WAIT_PAYLOAD,
    PS_WAIT_CRC
} parse_state_t;

/* 简单的异或校验，仅用于演示；真实协议请用 CRC */
static uint8_t checksum(const uint8_t *p, uint8_t n)
{
    uint8_t x = 0;
    for (uint8_t i = 0; i < n; i++) {
        x ^= p[i];
    }
    return x;
}

typedef struct {
    parse_state_t state;
    uint8_t  len;
    uint8_t  index;
    uint8_t  payload[MAX_PAYLOAD];
} parser_t;

/* 返回 true 表示收到一个完整帧 */
bool parser_feed(parser_t *p, uint8_t byte, uint8_t *out, uint8_t *out_len)
{
    switch (p->state) {
    case PS_WAIT_SOF:
        if (byte == SOF) {
            p->state = PS_WAIT_LEN;
        }
        break;

    case PS_WAIT_LEN:
        if (byte == 0u || byte > MAX_PAYLOAD) {
            p->state = PS_WAIT_SOF;      /* 长度非法：重新找帧头 */
        } else {
            p->len = byte;
            p->index = 0;
            p->state = PS_WAIT_PAYLOAD;
        }
        break;

    case PS_WAIT_PAYLOAD:
        p->payload[p->index++] = byte;
        if (p->index >= p->len) {
            p->state = PS_WAIT_CRC;
        }
        break;

    case PS_WAIT_CRC:
        p->state = PS_WAIT_SOF;
        if (byte == checksum(p->payload, p->len)) {
            memcpy(out, p->payload, p->len);
            *out_len = p->len;
            return true;
        }
        break;

    default:
        p->state = PS_WAIT_SOF;
        break;
    }
    return false;
}
易错

解析器里最危险的是长度字段。如果直接 memcpy(dst, src, len) 而不检查 len <= sizeof dst，一个错误的长度字节就能造成缓冲区溢出。所有来自外部的长度都必须先校验，再使用。

10.5溢出策略：丢新还是丢旧

策略适用场景后果

中断与主循环共享数据

11.1中断是“随时插进来的一段代码”

主循环正在执行 counter++，中断来了，中断服务程序（ISR）也执行 counter++，然后返回。直觉上结果应该是加 2，但实际可能只加了 1。

原因是：counter++ 在机器层面是读 → 改 → 写三步，中断可以插在任意两步之间。

动手看

临界区不是“更快的锁”，它只是短暂关闭中断；关得太久会影响系统响应。

11.2中断服务程序的三条纪律

短　只做必须立刻做的事：清标志、读数据、放进缓冲区、置事件。复杂处理交给主循环。
不阻塞　不能等待、不能延时、不能调用可能阻塞的函数（如带超时的队列发送）。
不重入　默认同一中断不会嵌套自己；如果开了嵌套，共享数据要额外保护。
isr_pattern.cC11
#include <stdint.h>
#include <stdbool.h>

static volatile bool     g_frame_ready;
static volatile uint8_t  g_frame[16];
static volatile uint8_t  g_frame_len;

/* 中断：只搬运和置标志 */
void UART_IRQHandler(void)
{
    uint8_t byte = UART_DATA;          /* 读数据寄存器（同时清标志） */
    if (g_frame_len < sizeof g_frame) {
        g_frame[g_frame_len++] = byte;
        if (byte == '\n') {
            g_frame_ready = true;
        }
    } else {
        g_frame_len = 0;               /* 溢出：丢弃这一帧 */
    }
}

/* 主循环：做解析、打印、业务 */
void app_poll(void)
{
    if (!g_frame_ready) {
        return;
    }
    g_frame_ready = false;
    /* 处理 g_frame[0..g_frame_len-1] */
    g_frame_len = 0;
}
易错

上面这段仍然有竞态：主循环处理到一半，中断又写入新数据，g_frame_len 被改，缓冲区内容被覆盖。正确做法是“双缓冲”或“把数据推进队列，主循环从队列取”，而不是共享同一个缓冲区。

11.3临界区：关中断的正确姿势

实现细节

临界区应只包住“必须原子”的那几行。能在临界区外做的计算、拷贝、判断，全部挪出去。临界区长度直接决定最坏中断延迟，这是实时系统里要测量的指标。

11.4更好的办法：单生产者单消费者队列

与其共享一大块数据，不如让中断只负责“把字节放进环形缓冲区”，主循环负责“取出来解析”。这样共享的只有两个索引，且各自只有一个写者。

11.5内存序：什么时候 volatile 也不够

在多核 MCU（如 Cortex-M7 + M4 双核、ESP32 双核）上，即使编译器不重排，CPU 也可能重排读写。这时需要内存屏障或 C11 原子类型：

barrier.c · 平台相关C11
/* 编译器屏障：阻止编译器重排，不阻止 CPU */
__asm volatile ("" ::: "memory");

/* ARM 数据内存屏障：保证屏障前的访问先完成 */
__DMB();

/* C11 原子：语义最清晰，但需要工具链支持 */
#include <stdatomic.h>
atomic_int flag;
atomic_store_explicit(&flag, 1, memory_order_release);
标准怎么说

C11 之前，C 语言没有多线程内存模型，volatile 也不提供原子性或顺序保证。C11 引入 <stdatomic.h> 后，跨线程共享才第一次有了标准语义。嵌入式工具链对 C11 原子的支持程度不一，使用前要确认。

12.1优化器的世界观：未定义行为不会发生

编译器优化时遵循一条铁律：如果程序有未定义行为，编译器可以对结果做任何假设。它不是“尽量保持你的本意”，而是“按标准允许的范围重新排列、删除、合并”。

ub_opt.cC11
#include <stdio.h>
#include <limits.h>

/* 有符号溢出是 UB：编译器可以假设 x + 1 不会溢出 */
int always_true(int x)
{
    return (x + 1) > x;
}

int main(void)
{
    printf("%d\n", always_true(INT_MAX));
    return 0;
}
GCC/Clang -O2 下可能输出
1

在数学上，INT_MAX + 1 应该变成 INT_MIN，(x+1) > x 应该为假。但编译器知道你“保证”不会溢出，于是直接把整个函数优化成 return 1。-O0 下通常输出 0，-O2 下输出 1——同一份代码，两种结果。如果开了 UBSan，它会在溢出发生的那一刻直接报错，这反而是最幸运的情况。

标准怎么说

“未定义行为”不是“结果不确定”，而是“标准不约束程序的任何行为”。这意味着编译器可以假设它永远不会发生，并据此做优化。想让溢出可预测，就改用无符号类型，或在运算前检查边界。

12.3为什么“空循环”消失了

delay.cC11
/* 想用空循环延时：不可靠 */
void delay_loop(void)
{
    for (volatile int i = 0; i < 100000; i++) {
        /* 空 */
    }
}

如果 i 不是 volatile，编译器会认为这个循环没有可观察的副作用，直接删掉。加了 volatile 后循环会保留，但延时长度仍取决于主频、编译选项和流水线，不能当作精确延时。

工程习惯

需要精确延时，用硬件定时器；需要“至少等一会儿”，用定时器或 RTOS 的阻塞延时。空循环只适合“上电后等晶振稳定”这类对精度没有要求的场合，而且要看芯片手册要求。

    /* ... */
    return 0;
}

12.5HardFault 之后看什么

Cortex-M 进入 HardFault 时，硬件会把关键寄存器压栈。调试器里通常能看到：

信息用途
PC / LR崩在哪条指令、从哪个函数返回
CFSR / HFSR区分总线错误、用法错误、内存管理错误
BFAR / MMFAR非法访问的地址
栈内容反推调用链与局部变量

更实用的做法是：在 HardFault 处理函数里把栈帧打印出来，或者点亮一个错误码 LED。产品现场没有调试器，能自己报告故障位置的固件才有维护价值。

综合项目：可复用命令解析器

把前面 12 讲拼成一个真正能用的模块：从字节流里切出命令，解析参数，查表执行，并把错误分类返回。

学完这一讲，你能

  • 设计一个与硬件无关的解析模块
  • 把环形缓冲、状态机、命令表组合起来
  • 为每条命令做参数校验与错误码
  • 在主机上写测试，再移植到目标板

13.1需求：从字节流到一条命令

目标：做一个与硬件无关的命令解析模块。输入是任意长度的字节流（可能半行到达、可能一行太长、可能有空行），输出是“命令名 + 参数 + 状态码”。它要能同时跑在 PC 和目标板上。

需求设计决策原因
逐字节输入cmd_parser_feed(p, ch) 返回 1 表示收到完整一行串口中断就是一个字节一个字节来的
行长上限CMD_LINE_MAX = 64，超长整行丢弃固定内存，不用 malloc；溢出必须显式处理
命令可扩展命令表 + 函数指针新增命令只加一行，不改分发逻辑
错误可区分cmd_status_t 枚举调用者能区分“未知命令 / 参数错 / 越界”
输出可控调用者提供 out 缓冲区与长度不依赖 printf，方便重定向到串口或测试
工程习惯

“解析”和“执行”分开：cmd_parser_feed 只负责切行，cmd_execute 只负责分发。这样解析器可以在没有硬件的情况下单独测试，执行器也可以被脚本直接调用。

13.2接口：cmd.h

cmd.hC11
#ifndef CMD_H
#define CMD_H

#include <stddef.h>

#define CMD_LINE_MAX 64

typedef enum {
    CMD_OK = 0,
    CMD_ERR_UNKNOWN,
    CMD_ERR_ARG,
    CMD_ERR_RANGE
} cmd_status_t;

typedef cmd_status_t (*cmd_handler_t)(int argc, char **argv, char *out, size_t out_len);

typedef struct {
    const char   *name;
    cmd_handler_t handler;
    const char   *usage;
} cmd_entry_t;

typedef struct {
    char   line[CMD_LINE_MAX];
    size_t len;
    int    overflow;
} cmd_parser_t;

void          cmd_parser_init(cmd_parser_t *p);
int           cmd_parser_feed(cmd_parser_t *p, char ch);
cmd_status_t  cmd_execute(const char *line, char *out, size_t out_len);
const char   *cmd_status_str(cmd_status_t st);

#endif

三个设计点值得注意：

  • cmd_handler_t 的返回值是 cmd_status_t，不是 int。错误码是接口的一部分。
  • out 与 out_len 由调用者提供，模块内部不分配内存，也不直接 printf。
  • cmd_parser_t 把“半行状态”显式保存下来，所以可以跨多次调用继续。

13.3实现：cmd.c

cmd.cC11
#include "cmd.h"

#include <stdio.h>
#include <string.h>

static cmd_status_t cmd_led(int argc, char **argv, char *out, size_t out_len);
static cmd_status_t cmd_read(int argc, char **argv, char *out, size_t out_len);
static cmd_status_t cmd_help(int argc, char **argv, char *out, size_t out_len);

static const cmd_entry_t g_cmds[] = {
    { "led",  cmd_led,  "led on|off" },
    { "read", cmd_read, "read <0-3>" },
    { "help", cmd_help, "help" },
};

void cmd_parser_init(cmd_parser_t *p)
{
    p->len = 0;
    p->overflow = 0;
}

int cmd_parser_feed(cmd_parser_t *p, char ch)
{
    if (ch == '\n' || ch == '\r') {
        if (p->overflow) {
            p->len = 0;
            p->overflow = 0;
            return -1;                 /* 上一行太长，已丢弃 */
        }
        p->line[p->len] = '\0';
        p->len = 0;
        return 1;
    }
    if (p->len + 1 >= sizeof p->line) {
        p->overflow = 1;               /* 标记溢出，等行结束再丢弃 */
        return 0;
    }
    p->line[p->len++] = ch;
    return 0;
}

static int split(char *s, char **argv, int max)
{
    int argc = 0;
    while (*s != '\0' && argc < max) {
        while (*s == ' ' || *s == '\t') {
            *s++ = '\0';
        }
        if (*s == '\0') {
            break;
        }
        argv[argc++] = s;
        while (*s != '\0' && *s != ' ' && *s != '\t') {
            s++;
        }
    }
    return argc;
}

cmd_status_t cmd_execute(const char *line, char *out, size_t out_len)
{
    char buf[CMD_LINE_MAX];
    size_t n = strlen(line);
    if (n >= sizeof buf) {
        return CMD_ERR_ARG;
    }
    memcpy(buf, line, n + 1);

    char *argv[6];
    int argc = split(buf, argv, 6);
    if (argc == 0) {
        return CMD_OK;                 /* 空行不算错误 */
    }

    for (size_t i = 0; i < sizeof g_cmds / sizeof g_cmds[0]; i++) {
        if (strcmp(argv[0], g_cmds[i].name) == 0) {
            return g_cmds[i].handler(argc, argv, out, out_len);
        }
    }
    snprintf(out, out_len, "unknown command: %s", argv[0]);
    return CMD_ERR_UNKNOWN;
}

const char *cmd_status_str(cmd_status_t st)
{
    switch (st) {
    case CMD_OK:          return "ok";
    case CMD_ERR_UNKNOWN: return "unknown";
    case CMD_ERR_ARG:     return "bad argument";
    case CMD_ERR_RANGE:   return "out of range";
    default:              return "?";
    }
}

static cmd_status_t cmd_led(int argc, char **argv, char *out, size_t out_len)
{
    if (argc != 2) {
        snprintf(out, out_len, "usage: led on|off");
        return CMD_ERR_ARG;
    }
    if (strcmp(argv[1], "on") == 0) {
        snprintf(out, out_len, "LED=1");
        return CMD_OK;
    }
    if (strcmp(argv[1], "off") == 0) {
        snprintf(out, out_len, "LED=0");
        return CMD_OK;
    }
    snprintf(out, out_len, "led: expected on|off");
    return CMD_ERR_ARG;
}

static cmd_status_t cmd_read(int argc, char **argv, char *out, size_t out_len)
{
    if (argc != 2) {
        snprintf(out, out_len, "usage: read <0-3>");
        return CMD_ERR_ARG;
    }
    if (argv[1][0] < '0' || argv[1][0] > '3' || argv[1][1] != '\0') {
        snprintf(out, out_len, "read: channel must be 0..3");
        return CMD_ERR_RANGE;
    }
    int ch = argv[1][0] - '0';
    snprintf(out, out_len, "CH%d=%d", ch, 100 + ch);
    return CMD_OK;
}

static cmd_status_t cmd_help(int argc, char **argv, char *out, size_t out_len)
{
    (void)argc;
    (void)argv;
    size_t used = 0;
    used += (size_t)snprintf(out + used, out_len - used, "commands:");
    for (size_t i = 0; i < sizeof g_cmds / sizeof g_cmds[0] && used < out_len; i++) {
        used += (size_t)snprintf(out + used, out_len - used, " %s", g_cmds[i].name);
    }
    return CMD_OK;
}
易错

split() 直接修改传入的缓冲区，所以 cmd_execute 先把行复制到本地 buf。如果直接改调用者的字符串，遇到字符串字面量就会崩溃——这是“能编译但运行时炸”的典型。

13.5移植到 MCU：只换输入输出

模块本身不含任何硬件相关代码。移植时只需要把“字节从哪来、结果到哪去”换掉：

app.c · 片段（平台相关，需配合 ring.c）C11
#include "cmd.h"
#include "ring.h"

static cmd_parser_t g_parser;
static ring_t       g_rx;

void app_init(void)
{
    cmd_parser_init(&g_parser);
    ring_init(&g_rx);
    uart_enable_rx_interrupt();
}

/* 串口中断：只把字节塞进环形缓冲区 */
void USART1_IRQHandler(void)
{
    uint8_t byte = uart_read_byte();
    (void)ring_push(&g_rx, byte);
}

/* 主循环：取出字节、喂给解析器、执行命令 */
void app_poll(void)
{
    uint8_t byte;
    while (ring_pop(&g_rx, &byte)) {
        if (cmd_parser_feed(&g_parser, (char)byte) == 1) {
            char out[96];
            cmd_status_t st = cmd_execute(g_parser.line, out, sizeof out);
            uart_write_str(cmd_status_str(st));
            uart_write_str(" ");
            uart_write_str(out);
            uart_write_str("\r\n");
        }
    }
}

注意 g_parser.line 在 feed 返回 1 之后仍然有效，直到下一次 feed 写入新字符。所以必须在同一轮循环里立刻执行，不能把指针存起来延后处理。

工程习惯

中断里只做 ring_push，解析和执行都在主循环。这样即使一帧命令很长、执行很慢，中断也不会被拖住；环形缓冲区满时丢弃并计数，不会阻塞。

A.4volatile 检查清单

  • 所有内存映射寄存器指针都加了 volatile
  • 中断与主循环共享的标志加了 volatile

  • 轮询循环里的读取确实每次都访问内存
  • 没有对 volatile 结构体做整体 memcpy 期望“原子快照”

A.7下一步：从裸机到 RTOS

到这里，你已经能写出“一个主循环 + 中断 + 环形缓冲区”的裸机程序。它能解决很多问题，但也会遇到瓶颈：

  • 多个任务都需要“等待”，主循环只能轮询，响应时间不确定。
  • 阻塞式延时会让其他逻辑全部停摆。
  • 共享资源越来越多，临界区越写越长。

第 3 册会讲 FreeRTOS 如何用任务、优先级、队列、信号量和互斥量来组织这些并发需求。你会发现，本册的环形缓冲区、状态机、临界区，在 RTOS 里都会以新的形式再次出现。
