9.1什么时候该用状态机

当一段逻辑满足下面任意两条，就该考虑状态机：

  • 行为依赖“之前发生过什么”，而不是只看当前输入。
  • 分支里出现多层嵌套的 if，且每层都在判断“现在处于哪个阶段”。
  • 需要处理超时、重试、异常恢复。
  • 同一件事在不同阶段有不同反应（例如“连接中”收到数据要丢弃，“已连接”收到数据要处理）。

状态机把这些隐含的“阶段”显式写出来：状态是现在在哪，事件是发生了什么，迁移是接下来去哪，动作是迁移时做什么。

9.2用 enum + switch 写一个

#include #include typedef enum { ST_IDLE = 0, ST_CONNECTING, ST_READY, ST_ERROR } state_t; typedef enum { EV_START = 0, EV_CONNECTED, EV_TIMEOUT, EV_FAIL, EV_RESET } event_t; typedef struct { state_t state; uint32_t retry; } fsm_t; static void on_enter(state_t s) { printf(" -> 进入状态 %d\n", (int)s); } void fsm_dispatch(fsm_t *f, event_t ev) { switch (f->state) { case ST_IDLE: if (ev == EV_START) { f->state = ST_CONNECTING; on_enter(f->state); } break; case ST_CONNECTING: if (ev == EV_CONNECTED) { f->state = ST_READY; f->retry = 0; on_enter(f->state); } else if (ev == EV_TIMEOUT || ev == EV_FAIL) { f->retry++; if (f->retry >= 3) { f->state = ST_ERROR; on_enter(f->state); } /* 否则留在 CONNECTING，等待下一次重试 */ } break; case ST_READY: if (ev == EV_FAIL || ev == EV_TIMEOUT) { f->state = ST_CONNECTING; on_enter(f->state); } break; case ST_ERROR: if (ev == EV_RESET) { f->state = ST_IDLE; f->retry = 0; on_enter(f->state); } break; default: f->state = ST_ERROR; break; } }
工程习惯

每个 switch 都写 default，把非法状态收敛到 ST_ERROR。状态变量被内存踩坏时，程序会进入可控的故障态，而不是执行随机的分支。

9.3表驱动：状态多了以后

#include typedef void (*action_fn)(fsm_t *f); typedef struct { state_t from; event_t event; state_t to; action_fn action; } transition_t; static void act_start(fsm_t *f) { (void)f; } static void act_fail(fsm_t *f) { f->retry++; } static const transition_t g_table[] = { { ST_IDLE, EV_START, ST_CONNECTING, act_start }, { ST_CONNECTING, EV_CONNECTED, ST_READY, NULL }, { ST_CONNECTING, EV_FAIL, ST_ERROR, act_fail }, { ST_ERROR, EV_RESET, ST_IDLE, NULL }, }; void fsm_dispatch_table(fsm_t *f, event_t ev) { for (size_t i = 0; i < sizeof g_table / sizeof g_table[0]; i++) { if (g_table[i].from == f->state && g_table[i].event == ev) { if (g_table[i].action != NULL) { g_table[i].action(f); } f->state = g_table[i].to; return; } } /* 没有匹配的迁移：记录日志或进入错误态 */ }
switch 实现表驱动
可读性状态少时直观状态多时一目了然
新增迁移改 switch 分支加一行表项
代码体积较小多一张常量表（放 Flash）
调试断点好打可以在循环里统一打日志
复杂动作直接写要拆成函数
动手看

状态机跑起来

点击事件按钮，看当前状态、允许的迁移和重试计数。注意“连接中”收到“已连接”和“失败”会走向完全不同的分支。

没有匹配迁移的事件会被忽略，并记录一条日志——这正是实际工程里应该做的。

9.4非阻塞：状态机的好搭档

状态机让“等”变成“记住现在在等”。不要在状态处理里写 delay_ms(1000)，而是记录时间戳，下次进来检查是否超时。

#include #include typedef struct { state_t state; uint32_t deadline_ms; } conn_t; /* 由 1 ms 定时器或主循环周期调用 */ void conn_tick(conn_t *c, uint32_t now_ms) { if (c->state == ST_CONNECTING && (int32_t)(now_ms - c->deadline_ms) >= 0) { fsm_dispatch((fsm_t *)c, EV_TIMEOUT); /* 超时，走重试逻辑 */ c->deadline_ms = now_ms + 500; /* 下一次超时时间 */ } }
实现细节

(int32_t)(now - deadline) >= 0 是处理计时器回绕的标准写法：无符号相减得到差值，转成有符号再比较，即使 now 溢出也能正确判断。直接写 now >= deadline 在回绕时会出错。

9.5状态机的常见错误

错误后果修正
在状态处理里阻塞等待整个系统卡住，其他事件得不到处理记录状态与时间戳，下次 tick 再判断
状态迁移没有默认分支非法状态执行随机逻辑default 进入错误态
事件在错误的状态被处理逻辑错乱，难以复现每个状态只处理明确列出的事件
进入/退出动作重复执行资源重复初始化或重复释放明确 on_enter / on_exit 只调用一次
状态变量被多处直接赋值绕过迁移规则只允许 fsm_dispatch 修改状态
动手练习 · 第 9 讲
  1. 为“按键消抖”画一个状态机：松开、按下抖动、稳定按下、长按。
  2. 把 9.2 节的 switch 版本改写成表驱动，并保证行为一致。
  3. 给连接状态机加一个“退避重试”策略：每次失败等待时间翻倍。
  4. 解释为什么状态机适合处理协议解析，而不适合处理纯计算。
参考答案与思路

1. 松开 →（检测到低电平）抖动 →（持续 20 ms 低）稳定按下 →（持续 1 s）长按；中途变高则回到松开。

2. 把每个 case 里的 if 拆成表项，动作抽成函数；注意“留在原状态”的迁移也要显式写出或明确忽略。

3. 保存 backoff_ms，失败时 backoff_ms = min(backoff_ms * 2, MAX)，成功时复位。

4. 协议解析天然有“阶段”（等帧头、等长度、等载荷、等校验），且事件是离散字节；纯计算没有状态依赖，用状态机反而增加开销。

自测：状态机里处理“等待超时”最合适的做法是？

状态机的前提是非阻塞：等待要变成“记住截止时间 + 周期检查”。阻塞等待会让整个主循环停摆，其他事件全部延迟。

本讲小结

  • 状态机把隐含的“阶段”显式化，适合有历史依赖、超时和异常恢复的逻辑。
  • 状态、事件、迁移、动作四要素要分清。
  • 状态少用 switch，状态多用表驱动。
  • 非阻塞的关键是“记录时间戳，周期检查”。
  • 只允许一个入口修改状态，非法状态收敛到错误态。
