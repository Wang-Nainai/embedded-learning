11.1中断是“随时插进来的一段代码”

主循环正在执行 counter++，中断来了，中断服务程序（ISR）也执行 counter++，然后返回。直觉上结果应该是加 2，但实际可能只加了 1。

原因是：counter++ 在机器层面是读 → 改 → 写三步，中断可以插在任意两步之间。

临界区不是“更快的锁”，它只是短暂关闭中断；关得太久会影响系统响应。

11.2中断服务程序的三条纪律

短　只做必须立刻做的事：清标志、读数据、放进缓冲区、置事件。复杂处理交给主循环。
不阻塞　不能等待、不能延时、不能调用可能阻塞的函数（如带超时的队列发送）。
不重入　默认同一中断不会嵌套自己；如果开了嵌套，共享数据要额外保护。
#include #include static volatile bool g_frame_ready; static volatile uint8_t g_frame[16]; static volatile uint8_t g_frame_len; /* 中断：只搬运和置标志 */ void UART_IRQHandler(void) { uint8_t byte = UART_DATA; /* 读数据寄存器（同时清标志） */ if (g_frame_len < sizeof g_frame) { g_frame[g_frame_len++] = byte; if (byte == '\n') { g_frame_ready = true; } } else { g_frame_len = 0; /* 溢出：丢弃这一帧 */ } } /* 主循环：做解析、打印、业务 */ void app_poll(void) { if (!g_frame_ready) { return; } g_frame_ready = false; /* 处理 g_frame[0..g_frame_len-1] */ g_frame_len = 0; }
易错

上面这段仍然有竞态：主循环处理到一半，中断又写入新数据，g_frame_len 被改，缓冲区内容被覆盖。正确做法是“双缓冲”或“把数据推进队列，主循环从队列取”，而不是共享同一个缓冲区。

11.3临界区：关中断的正确姿势

#include /* Cortex-M：保存并恢复 PRIMASK，支持嵌套 */ static inline uint32_t enter_critical(void) { uint32_t primask = __get_PRIMASK(); __disable_irq(); return primask; } static inline void exit_critical(uint32_t primask) { __set_PRIMASK(primask); } void update_shared(void) { uint32_t pm = enter_critical(); g_counter++; /* 读改写被保护 */ exit_critical(pm); }
做法问题
__disable_irq(); ...; __enable_irq();嵌套调用时，内层退出会提前开中断
关中断里调用 printf / 延时中断被关闭太久，系统失去响应
关中断里调用可能阻塞的 RTOS API未定义行为或死锁
只保护写、不保护读读到一半仍可能被改
实现细节

临界区应只包住“必须原子”的那几行。能在临界区外做的计算、拷贝、判断，全部挪出去。临界区长度直接决定最坏中断延迟，这是实时系统里要测量的指标。

11.4更好的办法：单生产者单消费者队列

与其共享一大块数据，不如让中断只负责“把字节放进环形缓冲区”，主循环负责“取出来解析”。这样共享的只有两个索引，且各自只有一个写者。

/* 中断：生产者 */ void UART_IRQHandler(void) { uint8_t byte = UART_DATA; if (!ring_push(&g_rx, byte)) { g_rx_overflow++; /* 记录溢出，不要静默丢弃 */ } } /* 主循环：消费者 */ void app_poll(void) { uint8_t byte; while (ring_pop(&g_rx, &byte)) { parser_feed(&g_parser, byte); } }

这就是第 10 讲的环形缓冲区在真实系统里的用法：中断生产、主循环消费。它把“共享大块数据”变成了“共享两个索引”，竞态面小得多。

11.5内存序：什么时候 volatile 也不够

在多核 MCU（如 Cortex-M7 + M4 双核、ESP32 双核）上，即使编译器不重排，CPU 也可能重排读写。这时需要内存屏障或 C11 原子类型：

/* 编译器屏障：阻止编译器重排，不阻止 CPU */ __asm volatile ("" ::: "memory"); /* ARM 数据内存屏障：保证屏障前的访问先完成 */ __DMB(); /* C11 原子：语义最清晰，但需要工具链支持 */ #include atomic_int flag; atomic_store_explicit(&flag, 1, memory_order_release);
标准怎么说

C11 之前，C 语言没有多线程内存模型，volatile 也不提供原子性或顺序保证。C11 引入 <stdatomic.h> 后，跨线程共享才第一次有了标准语义。嵌入式工具链对 C11 原子的支持程度不一，使用前要确认。

参考答案与思路

1. 编译器优化（轮询被缓存）、非原子访问（32 位变量分两次写）、竞态（读改写被插入）。

2. 临界区可能嵌套：内层退出时如果直接开中断，外层还没执行完就被打断了。保存/恢复能保证“退出时回到进入前的状态”。

3. 中断 push，主循环 pop，解析器消费字节；共享 head/tail，各自单写。

4. volatile 解决“访问被优化”，用于寄存器和简单标志；atomic 解决“读改写不可分割 + 内存序”，用于计数器、跨核标志。

自测：主循环和中断都执行 g_count++，最终少加了一次。最直接的原因是？

g_count++ 是读、加、写三步；中断插在中间时，两个上下文都基于旧值计算，后写的覆盖先写的。volatile 无法解决这个问题。

本讲小结

  • 中断可以插在任意指令之间，读改写因此可能丢失更新。
  • ISR 三条纪律：短、不阻塞、不重入。
  • 临界区要保存/恢复中断状态，且尽量短。
  • SPSC 环形缓冲区把共享面缩到两个索引。
  • 多核场景需要屏障或 C11 原子，volatile 不够。
