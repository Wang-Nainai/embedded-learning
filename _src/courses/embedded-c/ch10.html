10.1为什么是“环形”

串口数据随时可能到达，CPU 不能停下来等。最直接的做法是开一个大数组，来一个字节存一个——但数组总会满，满了就要搬移数据，搬移又要时间。

环形缓冲区（ring buffer / FIFO）用固定大小的数组 + 两个指针解决这个问题：写指针向前走，走到末尾就回到开头；读指针同理。不需要搬移，插入和取出都是 O(1)。

10.2怎么区分“满”和“空”

如果只有 head 和 tail，那么 head == tail 既可能是空，也可能是满。三种常见解法：

方案做法容量代价
浪费一个槽位(head + 1) % N == tail 判满N-1少存一个元素，逻辑最简单
额外计数维护 count，0 为空、N 为满N多一个变量，读写都要更新
镜像索引用 2N 的数组，head/tail 不回绕，靠掩码取模N多占一倍地址空间（不一定要多占内存）
#ifndef RING_H #define RING_H #include #include #include #define RING_CAP 64 typedef struct { uint8_t buf[RING_CAP]; volatile uint16_t head; /* 写索引：只有生产者修改 */ volatile uint16_t tail; /* 读索引：只有消费者修改 */ } ring_t; void ring_init(ring_t *r); bool ring_push(ring_t *r, uint8_t byte); /* 满则返回 false */ bool ring_pop(ring_t *r, uint8_t *out); /* 空则返回 false */ size_t ring_count(const ring_t *r); bool ring_is_empty(const ring_t *r); bool ring_is_full(const ring_t *r); #endif #include "ring.h" void ring_init(ring_t *r) { r->head = 0; r->tail = 0; } bool ring_is_empty(const ring_t *r) { return r->head == r->tail; } bool ring_is_full(const ring_t *r) { return (uint16_t)((r->head + 1u) % RING_CAP) == r->tail; } size_t ring_count(const ring_t *r) { return (size_t)((r->head + RING_CAP - r->tail) % RING_CAP); } bool ring_push(ring_t *r, uint8_t byte) { uint16_t next = (uint16_t)((r->head + 1u) % RING_CAP); if (next == r->tail) { return false; /* 满：丢弃或由调用者处理 */ } r->buf[r->head] = byte; r->head = next; /* 先写数据，再移动指针 */ return true; } bool ring_pop(ring_t *r, uint8_t *out) { if (r->head == r->tail) { return false; /* 空 */ } *out = r->buf[r->tail]; r->tail = (uint16_t)((r->tail + 1u) % RING_CAP); return true; }
工程习惯

“先写数据，再移动 head”是单生产者单消费者场景下的关键顺序：消费者看到 head 前进时，数据一定已经写好了。反过来（先动指针再写数据）会让消费者读到旧值。更严格的多核场景还需要内存屏障。

满的时候 push 返回 false，不是覆盖旧数据——丢新数据还是丢旧数据，是业务策略，必须显式决定。

10.3字节流不是消息流

串口给你的是连续的字节。一次中断可能收到半个帧，也可能收到一帧半。解析器必须自己解决三件事：

粘连

两次数据粘在一起：[帧1][帧2]。必须按长度切开，不能假设“一次读 = 一帧”。

分片

一帧分几次到达：[帧头+长度] 然后 [载荷]。必须缓存中间状态。

噪声

总线上出现乱码。必须能重新同步到帧头，而不是一直错位。

10.4解析状态机

#include #include #include #define SOF 0xA5u #define MAX_PAYLOAD 32u typedef enum { PS_WAIT_SOF = 0, PS_WAIT_LEN, PS_WAIT_PAYLOAD, PS_WAIT_CRC } parse_state_t; /* 简单的异或校验，仅用于演示；真实协议请用 CRC */ static uint8_t checksum(const uint8_t *p, uint8_t n) { uint8_t x = 0; for (uint8_t i = 0; i < n; i++) { x ^= p[i]; } return x; } typedef struct { parse_state_t state; uint8_t len; uint8_t index; uint8_t payload[MAX_PAYLOAD]; } parser_t; /* 返回 true 表示收到一个完整帧 */ bool parser_feed(parser_t *p, uint8_t byte, uint8_t *out, uint8_t *out_len) { switch (p->state) { case PS_WAIT_SOF: if (byte == SOF) { p->state = PS_WAIT_LEN; } break; case PS_WAIT_LEN: if (byte == 0u || byte > MAX_PAYLOAD) { p->state = PS_WAIT_SOF; /* 长度非法：重新找帧头 */ } else { p->len = byte; p->index = 0; p->state = PS_WAIT_PAYLOAD; } break; case PS_WAIT_PAYLOAD: p->payload[p->index++] = byte; if (p->index >= p->len) { p->state = PS_WAIT_CRC; } break; case PS_WAIT_CRC: p->state = PS_WAIT_SOF; if (byte == checksum(p->payload, p->len)) { memcpy(out, p->payload, p->len); *out_len = p->len; return true; } break; default: p->state = PS_WAIT_SOF; break; } return false; }
易错

解析器里最危险的是长度字段。如果直接 memcpy(dst, src, len) 而不检查 len <= sizeof dst，一个错误的长度字节就能造成缓冲区溢出。所有来自外部的长度都必须先校验，再使用。

10.5溢出策略：丢新还是丢旧

策略适用场景后果
拒绝新数据数据必须完整，宁可丢新也不能乱序旧数据保留，新数据丢失，需要计数告警
覆盖最旧只关心最新状态（如传感器最新值）消费者可能看到跳变
扩容主机环境，内存充足嵌入式里通常不可行（堆碎片、确定性差）

无论选哪种，都要记录溢出次数。一个默默丢数据的系统，比一个明确报错的系统更难排查。

参考答案与思路

1. count 版本容量是 N，但 push/pop 都要读改写 count；在 SPSC 场景下，count 会被两边同时修改，需要原子操作或临界区。浪费槽位版本只有一个生产者写 head、一个消费者写 tail，天然无锁。

2. head、tail 和 buf（通过指针间接访问）都需要保证编译器不缓存；通常把 head/tail 声明为 volatile，buf 的可见性靠写入顺序与编译器屏障保证。

3. 在 parser_t 里加 last_ms，每次 feed 更新时间；周期函数检查差值，超时则复位状态。

4. 用表驱动测试：输入字节序列、期望的返回值与输出帧；覆盖空、半帧、超长、校验错、连续多帧。

自测：容量为 8、采用“浪费一个槽位”判满的环形缓冲区，最多能存几个字节？

当 (head+1)%8 == tail 时判满，所以 head 和 tail 之间总要空一格，实际可用 7 个。

本讲小结

  • 环形缓冲区用固定内存实现 O(1) 的入队/出队，不需要搬移。
  • 满/空判定有三种方案，各有容量与并发代价。
  • 字节流必须按“粘连、分片、噪声”三种情况设计解析器。
  • 外部长度字段必须先校验再使用。
  • 溢出策略要显式选择，并记录溢出次数。
