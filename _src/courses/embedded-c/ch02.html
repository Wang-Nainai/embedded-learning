2.1寄存器就是一个固定地址

“配置 GPIO”听起来抽象，落到代码上只有一句话：往某个固定地址写一个特定宽度的值。芯片手册给出的寄存器表，本质上是一张“地址 + 位定义”的说明书。

#include #define GPIOA_BASE 0x40020000UL #define GPIOA_MODER (*(volatile uint32_t *)(GPIOA_BASE + 0x00UL)) #define GPIOA_ODR (*(volatile uint32_t *)(GPIOA_BASE + 0x14UL)) void led_init(void) { /* 把 PA5 配置为通用输出：MODER[11:10] = 01 */ GPIOA_MODER &= ~(3UL << 10); /* 先清两位 */ GPIOA_MODER |= (1UL << 10); /* 再写 01 */ GPIOA_ODR |= (1UL << 5); /* 输出高电平 */ }

拆开看这个宏：

  • 0x40020000UL 是整数常量，UL 保证它是 unsigned long，避免在 16 位 int 的平台上溢出。
  • (volatile uint32_t *) 把整数转换成“指向 32 位寄存器的指针”。
  • 外面的 * 解引用，于是 GPIOA_MODER 可以像普通变量一样赋值——但每次访问都会真的读写那个地址。
标准怎么说

把整数转成指针、再解引用一个“不是 C 对象”的地址，严格来说超出了 C 标准描述的范围（标准只保证对象和数组内部的指针算术）。这是实现定义 + 平台约定：编译器明确支持内存映射 I/O，芯片手册保证该地址有效。写驱动时必须同时信任这两份文档。

2.2volatile：让编译器“每次都真的去读”

没有 volatile 时，编译器可以合理地假设“这个变量的值不会自己变”，于是把多次读取合并成一次，甚至把整个循环优化掉。

/* 错误：编译器可能只读一次 STATUS，然后死循环 */ while (STATUS == 0) { } /* 正确：每次都从地址重新读取 */ while (*(volatile uint32_t *)STATUS_ADDR == 0) { }

volatile 告诉编译器三件事：

不能省

每次访问都必须真实发生，不能合并、不能缓存到寄存器。

不能重排

同一线程内，volatile 访问之间的顺序不会被编译器调换。

仅此而已

它不保证原子性，不保证多核之间的可见性，也不是锁。

易错

“用 volatile 就能在多任务/中断里安全共享变量”是错误结论。volatile 只解决“编译器优化掉访问”，不解决“读到一半被中断打断”。第 11 讲会专门处理这个问题。

2.3厂商头文件为什么那样写

真实工程不会为每个寄存器写一个宏，而是用结构体把一组寄存器连续排列，再用基地址转成指针：

#include typedef struct { volatile uint32_t MODER; /* 0x00 */ volatile uint32_t OTYPER; /* 0x04 */ volatile uint32_t OSPEEDR; /* 0x08 */ volatile uint32_t PUPDR; /* 0x0C */ volatile uint32_t IDR; /* 0x10 */ volatile uint32_t ODR; /* 0x14 */ volatile uint32_t BSRR; /* 0x18 */ volatile uint32_t LCKR; /* 0x1C */ volatile uint32_t AFR[2]; /* 0x20, 0x24 */ } GPIO_TypeDef; #define GPIOA ((GPIO_TypeDef *)0x40020000UL) void led_on(void) { GPIOA->BSRR = (1UL << 5); /* 写 1 置位，单次写，天然原子 */ }

这种写法依赖两个前提：结构体成员之间没有填充，且每个成员都是 4 字节。只要成员全是 uint32_t，在常见 ABI 下就成立；一旦混入 uint8_t，就可能出现填充，寄存器偏移全错。厂商头文件通常会用编译期断言检查偏移。

实现细节

CMSIS 把这种结构体指针封装成 GPIOA 这样的宏，并加上 __IO（即 volatile）修饰。不同厂商命名不同，但套路一致：基地址 + 结构体偏移 + volatile。

2.4读改写：一行 C 其实是三步

REG |= (1 << 3); 看起来是一个动作，编译后通常是：

读　把 REG 的 32 位值从外设读进 CPU 寄存器。
改　在 CPU 里做按位或。
写　把结果写回 REG。

如果在这三步之间来了中断，而中断也修改了同一个寄存器，那么中断的修改会被主流程的“写回”覆盖——这叫读改写丢失更新。

/* 主循环 */ REG |= (1u << 3); /* 中断里 */ REG |= (1u << 7); /* 可能的执行顺序： 主：读 REG（bit7=0） 中断：读 REG（bit7=0），写回 bit7=1 主：写回自己算出的值（bit7 仍是 0）→ 中断的修改丢了 */
正确做法

优先使用硬件提供的原子置位/清位寄存器（例如 STM32 的 BSRR：写 1 置位、写 0 无影响；写 1 到高 16 位清位）。没有这种寄存器时，用临界区保护整段读改写，或者用位带（如果芯片支持）。

2.5写 1 清除：不能想当然

有些状态寄存器的语义是“写 1 清除”（write-1-to-clear）。这时 REG &= ~(1 << n) 不但清不掉，还可能把其他位清掉，因为写 0 在该位上“无动作”，而其他位写 0 也可能触发清除。

/* 假设 bit0..bit3 都是 write-1-to-clear 的标志位 */ REG = (1u << 2); /* 只清 bit2：直接赋值，不要读改写 */
工程习惯

读寄存器手册时，先确认每个字段的访问类型：RW、RO、W1C、RC_W0……访问类型比位定义更容易被忽略，也更容易导致“明明写了却没效果”。

32 位寄存器位图

点击任意位翻转它，观察十六进制值，以及“置位 / 清位”对应的 C 表达式。这就是写驱动时每天在做的事。

位编号从 0（最低位）开始。写寄存器时务必用 1u << n，不要用有符号的 1 << 31。

参考答案与思路

1. REG = (REG & ~(0xFUL << 12)) | (0xAUL << 12);。先清 4 位，再写入目标值。

2. 非 volatile 时编译器可以把 REG 读一次存到寄存器，循环条件不再重新读内存；如果初值为 0，就永远不结束；如果编译器认为循环无副作用，还可能整个删掉。

3. 编译器会在 uint8_t 后插入填充，使下一个 uint32_t 对齐到 4 字节，后续所有寄存器偏移都错位。

4. 当同一寄存器会被主循环和中断（或两个任务）同时读改写，且硬件没有原子置位/清位寄存器时。

自测：volatile 能保证下面哪一项？

volatile 只约束编译器，不提供原子性，也不提供内存屏障语义（跨核/跨设备的顺序需要额外手段）。原子性要靠硬件指令、临界区或 C11 原子类型。

本讲小结

  • 寄存器访问 = 固定地址 + 正确宽度 + volatile。
  • 结构体映射依赖“无填充”这一前提，混入小类型会错位。
  • REG |= x 是读改写三步，可能丢失并发修改。
  • 优先用硬件提供的原子置位/清位寄存器。
