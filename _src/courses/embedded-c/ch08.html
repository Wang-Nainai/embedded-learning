8.1为什么驱动要分层

如果应用代码里直接写 GPIOA->ODR |= (1<<5)，那么换一颗芯片就要改遍所有业务逻辑。分层的目标只有一个：把“会变的”关在一个小盒子里。

8.2接口长什么样

一套稳定的设备接口通常只有五类函数：初始化、销毁、读、写、控制。返回统一用错误码，而不是“成功返回 0、失败返回 -1”混着来。

#ifndef I2C_IF_H #define I2C_IF_H #include #include typedef enum { I2C_OK = 0, I2C_ERR_ARG, /* 参数非法 */ I2C_ERR_NACK, /* 从机无应答 */ I2C_ERR_BUSY, /* 总线忙 / 超时 */ I2C_ERR_IO /* 其他硬件错误 */ } i2c_status_t; /* 传输描述：只描述“要做什么”，不暴露寄存器细节 */ typedef struct { uint8_t addr; /* 7 位地址 */ const uint8_t *tx; size_t tx_len; uint8_t *rx; size_t rx_len; } i2c_msg_t; i2c_status_t i2c_transfer(const i2c_msg_t *msg, uint32_t timeout_ms); const char *i2c_status_str(i2c_status_t st); #endif
工程习惯

错误码用 enum 而不是裸 int，有三个好处：调用者能 switch 出所有情况、日志能打印名字、新增错误码时不会和已有数值冲突。i2c_status_str 让日志更可读。

8.3头文件依赖：能少包含就少包含

/* 应用头文件里包含了整个驱动头文件 */ #include "bsp_i2c.h" #include "sensor_xxx_v2.h" typedef struct { sensor_xxx_t dev; /* 调用者被迫知道驱动的完整定义 */ } app_ctx_t;

这会导致：改驱动头文件 → 所有包含应用头文件的文件全部重编译；驱动头文件里的宏还可能污染应用命名空间。

#ifndef APP_CTX_H #define APP_CTX_H #include /* 前向声明：只告诉编译器“有这么个类型”，不暴露内部 */ typedef struct sensor sensor_t; typedef struct { sensor_t *sensor; /* 指针，不需要完整定义 */ uint32_t period_ms; } app_ctx_t; #endif
做法效果
头文件只包含“自己需要”的头文件减少传递依赖
能用前向声明就不用 include结构体指针、函数参数都可以
用 <stdint.h> 而不是厂商大杂烩头文件避免命名冲突
每个头文件都有包含守卫防止重复定义

8.4用条件编译适配不同芯片

#ifndef BOARD_H #define BOARD_H #if defined(BOARD_STM32F4) # include "stm32f4xx_hal.h" # define LED_PORT GPIOA # define LED_PIN 5u #elif defined(BOARD_ESP32) # include "driver/gpio.h" # define LED_PIN GPIO_NUM_2 #else # error "未选择目标板：请定义 BOARD_STM32F4 或 BOARD_ESP32" #endif void board_led_init(void); void board_led_set(int on); #endif

#error 很重要：配置缺失时立刻停止编译，而不是生成一个“看起来能过、实际引脚全错”的固件。

实现细节

条件编译只适合少量、稳定的差异。如果每个函数里都塞满 #ifdef，代码会迅速不可读。更好的做法是把差异收敛到 board_* 或 bsp_* 这一层，上层保持单一实现。

8.5一个完整的模块骨架

#ifndef BSP_LED_H #define BSP_LED_H #include void bsp_led_init(void); void bsp_led_set(bool on); void bsp_led_toggle(void); #endif #include "bsp_led.h" #include "board.h" static bool s_state; void bsp_led_init(void) { /* 具体寄存器操作依赖芯片，这里用伪接口表示 */ board_gpio_config_output(LED_PORT, LED_PIN); s_state = false; board_gpio_write(LED_PORT, LED_PIN, false); } void bsp_led_set(bool on) { s_state = on; board_gpio_write(LED_PORT, LED_PIN, on); } void bsp_led_toggle(void) { bsp_led_set(!s_state); }
工程习惯

static bool s_state; 保存了“软件认为的当前状态”。如果外部（中断、其他模块）也能改这个引脚，软件状态就会和硬件不一致。要么保证唯一入口，要么每次从硬件回读。

8.6模块化的检查清单

  • 头文件里只有声明、类型、宏，没有变量定义
  • 每个 .c 都有对应的 .h，接口与实现同名
  • 模块内部函数用 static
  • 没有跨模块的全局变量，只有 xxx_get() / xxx_set()
  • 依赖方向单一，没有循环包含
  • 错误码统一，调用者能区分“参数错 / 忙 / 硬件错”

参考答案与思路

1. key_init()、key_is_pressed()、key_on_event(cb, ctx)；事件类型用 enum，回调在中断或扫描任务里触发。

2. 厂商头文件通常很大且包含大量宏与类型，任何包含它的文件在它变化时都要重编译；还会把芯片相关名字带进上层命名空间。

3. 去掉 s_state，toggle 先 board_gpio_read 再写反值。代价是多一次读，且读改写之间可能被中断打断。

4. 放在芯片层（bsp_delay），因为实现依赖 SysTick 或定时器；上层只调用毫秒级接口，不关心怎么计时。

自测：应用层需要持有 sensor_t 指针，但不想暴露其内部结构，头文件里应该？

前向声明只引入“类型名字”，不暴露成员布局，指针大小固定，因此足够使用；定义留在驱动内部，调用者无法依赖内部字段。

本讲小结

  • 分层的目的：把芯片差异关在最小范围内。
  • 接口统一错误码，调用者才能正确处理失败。
  • 头文件只放必要内容，能用前向声明就不 include。
  • 条件编译收敛到 board/bsp 层，配置缺失用 #error。
  • 模块内部函数一律 static，全局状态要有唯一入口。
