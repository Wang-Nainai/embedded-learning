12.1优化器的世界观：未定义行为不会发生

编译器优化时遵循一条铁律：如果程序有未定义行为，编译器可以对结果做任何假设。它不是“尽量保持你的本意”，而是“按标准允许的范围重新排列、删除、合并”。

#include #include /* 有符号溢出是 UB：编译器可以假设 x + 1 不会溢出 */ int always_true(int x) { return (x + 1) > x; } int main(void) { printf("%d\n", always_true(INT_MAX)); return 0; } 1

在数学上，INT_MAX + 1 应该变成 INT_MIN，(x+1) > x 应该为假。但编译器知道你“保证”不会溢出，于是直接把整个函数优化成 return 1。-O0 下通常输出 0，-O2 下输出 1——同一份代码，两种结果。如果开了 UBSan，它会在溢出发生的那一刻直接报错，这反而是最幸运的情况。

标准怎么说

“未定义行为”不是“结果不确定”，而是“标准不约束程序的任何行为”。这意味着编译器可以假设它永远不会发生，并据此做优化。想让溢出可预测，就改用无符号类型，或在运算前检查边界。

实现细节

GCC/Clang 默认开启严格别名优化（-fstrict-aliasing，包含在 -O2 里）。有些老代码靠 -fno-strict-aliasing 续命，但正确做法是改代码：用 memcpy、union（受限）或 may_alias 属性。

12.3为什么“空循环”消失了

/* 想用空循环延时：不可靠 */ void delay_loop(void) { for (volatile int i = 0; i < 100000; i++) { /* 空 */ } }

如果 i 不是 volatile，编译器会认为这个循环没有可观察的副作用，直接删掉。加了 volatile 后循环会保留，但延时长度仍取决于主频、编译选项和流水线，不能当作精确延时。

工程习惯

需要精确延时，用硬件定时器；需要“至少等一会儿”，用定时器或 RTOS 的阻塞延时。空循环只适合“上电后等晶振稳定”这类对精度没有要求的场合，而且要看芯片手册要求。

12.4把问题挡在运行时之前

编译期

断言与警告

_Static_assert 检查布局与常量；-Wall -Wextra -Werror 把警告变成错误。

运行期

assert 与日志

assert(p != NULL) 在调试版本捕获非法状态；发布版本可关闭，但要保留错误码。

工具

sanitizer 与调试器

主机上用 ASan/UBSan 跑逻辑；目标板上用 GDB + 断点 + 寄存器查看。

#include #include int parse(const uint8_t *buf, size_t len) { assert(buf != NULL); /* 调试版本：违反直接 abort */ assert(len <= 64); /* 约定上限，防止越界 */ if (buf == NULL || len > 64) { return -1; /* 发布版本：返回错误码，不崩溃 */ } /* ... */ return 0; }

12.5HardFault 之后看什么

Cortex-M 进入 HardFault 时，硬件会把关键寄存器压栈。调试器里通常能看到：

信息用途
PC / LR崩在哪条指令、从哪个函数返回
CFSR / HFSR区分总线错误、用法错误、内存管理错误
BFAR / MMFAR非法访问的地址
栈内容反推调用链与局部变量

更实用的做法是：在 HardFault 处理函数里把栈帧打印出来，或者点亮一个错误码 LED。产品现场没有调试器，能自己报告故障位置的固件才有维护价值。

12.6让硬件相关代码也能在主机上测试

把“读寄存器”抽成接口，业务逻辑就变成纯 C，可以在 PC 上编译、跑单元测试：

#ifndef HAL_H #define HAL_H #include /* 只声明，不实现：目标板提供真实实现，主机测试提供假实现 */ uint32_t hal_gpio_read(uint8_t pin); void hal_gpio_write(uint8_t pin, int level); uint32_t hal_tick_ms(void); #endif #include "hal.h" static uint32_t g_fake_tick; uint32_t hal_gpio_read(uint8_t pin) { (void)pin; return 0; } void hal_gpio_write(uint8_t pin, int level) { (void)pin; (void)level; } uint32_t hal_tick_ms(void) { return g_fake_tick; } void fake_tick_advance(uint32_t ms) { g_fake_tick += ms; }

这样，状态机、解析器、控制逻辑都能在主机上跑测试；只有 hal_* 的实现需要在真实硬件上验证。这是嵌入式工程里投入产出比最高的一个习惯。

参考答案与思路

1. -O0 可能输出 0，-O2 输出 1；如果编译器更激进，甚至可能把整个调用折叠成常量。

2. 用 SysTick 或硬件定时器计数，或调用 RTOS 的 vTaskDelay；空循环只能用于对时间无要求的场合。

3. 它允许编译器假设“不同类型的指针不会指向同一对象”，从而放心地把值缓存在寄存器里、调整读写顺序。没有这条规则，几乎无法做有效的别名分析。

4. 编译期用 _Static_assert 检查缓冲区大小；运行期检查空指针、长度、状态；测试时用 ASan/UBSan 跑异常输入。

自测：for (int i = 0; i < 100000; i++) { } 在 -O2 下最可能发生什么？

循环没有可观察的副作用，编译器可以直接删除。要保留必须让循环体有 volatile 访问或调用外部函数，但即使保留，延时长度也不可靠。

本讲小结

  • 编译器可以假设 UB 不会发生，因此优化后的行为可能“反直觉”。
  • 五类高频 UB：有符号溢出、越界、空指针、严格别名、未初始化读取。
  • 空循环延时不精确，甚至会被删除。
  • 三层防护：编译期断言、运行期检查、sanitizer 测试。
  • 把硬件访问抽成 HAL，业务逻辑就能在主机上测试。
