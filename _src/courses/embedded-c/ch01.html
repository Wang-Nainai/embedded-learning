1.1两种程序，两种“出生方式”

你在电脑上运行程序时，操作系统已经替你做了一大堆准备：分配地址空间、加载可执行文件、初始化 C 运行库、把参数传给 main。单片机上没有操作系统，上电那一刻，除了 Flash 里的机器码和一块未初始化的 SRAM，什么都没有。

同一个 main，两种运行环境
PC（hosted）MCU（freestanding）
谁加载程序操作系统复位后从固定地址取指令
谁初始化内存加载器 + C 运行库启动代码（startup）
标准库完整 libc精简版（如 newlib-nano），很多函数不可用
程序结束返回操作系统通常不允许返回，main 里是死循环
地址空间虚拟地址，由 MMU 映射物理地址，直接对应 Flash / SRAM / 外设
标准怎么说

C 标准区分 hosted 和 freestanding 两种实现。freestanding 实现只需要提供极少数头文件（<stddef.h>、<stdint.h>、<limits.h> 等），不保证有 printf、文件系统或堆。这就是为什么在单片机上用 printf 往往要重定向 _write，而且浮点格式化会显著增加 Flash 占用。

1.2从上电到 main：五步

取向量表　Cortex-M 在地址 0x00000000（或重映射后的 Flash 起始）取第一个字作为初始栈指针，第二个字作为复位入口地址。
执行 Reset_Handler　启动代码在这里运行，通常用汇编写成，还没进入 C 世界。
复制 .data　已初始化的全局/静态变量，初值存在 Flash，运行时必须复制到 SRAM，因为 SRAM 可写。
清零 .bss　未初始化（或初始化为 0）的全局/静态变量，按 C 标准必须是 0，启动代码把这块 SRAM 全部写 0。
调用 main　设置好栈之后跳进 main。很多工程的 main 末尾是 while (1)，永不返回。

1.3内存映射：地址不是“内存”，是“硬件”

在 MCU 上，地址空间是一张统一的地图：一部分地址接 Flash，一部分接 SRAM，一部分接外设寄存器。往 0x40020014 写一个数，可能不是“存起来”，而是立刻改变某个引脚的电平。

1.4链接脚本：谁决定变量住在哪

PC 上由链接器默认脚本安排地址；裸机上通常要自己写（或用厂商提供的）链接脚本。它至少描述两件事：存储器区域和段如何摆放。

MEMORY { FLASH (rx) : ORIGIN = 0x08000000, LENGTH = 512K RAM (rwx) : ORIGIN = 0x20000000, LENGTH = 128K } SECTIONS { .text : { KEEP(*(.isr_vector)) /* 向量表必须放在最前面 */ *(.text*) *(.rodata*) } > FLASH .data : { *(.data*) } > RAM AT > FLASH /* 运行在 RAM，初值存在 FLASH */ .bss : { *(.bss*) *(COMMON) } > RAM }
实现细节

> RAM AT > FLASH 是理解启动代码的关键：.data 段的运行地址在 RAM，加载地址在 Flash。启动代码要按这两个地址把初值搬过去。搬多少、从哪搬，由链接器生成的符号（如 _sdata、_edata、_sidata）告诉启动代码。

1.5交叉编译：在 x86 上生成 ARM 代码

你的电脑是 x86-64，目标板是 ARM Cortex-M。编译器本身跑在 x86 上，但生成的是 ARM 指令，这叫交叉编译。工具链前缀通常写明目标，例如 arm-none-eabi-gcc。

arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=c11 \ -Wall -Wextra -O2 -g \ -ffunction-sections -fdata-sections \ -T link.ld -nostartfiles \ main.c startup.c -o app.elf arm-none-eabi-size app.elf # 看 text / data / bss 占用 arm-none-eabi-objdump -h app.elf # 看各段地址与大小
选项作用
-mcpu= / -mthumb指定内核与指令集；选错会直接跑飞
-nostartfiles不使用工具链默认启动文件，改用工程自己的 startup
-T link.ld指定链接脚本
-ffunction-sections -fdata-sections每个函数/变量单独成段，配合 --gc-sections 删除未用代码
-specs=nano.specs使用 newlib-nano，显著减小 Flash 占用（GCC 工具链）
-Wl,-Map=app.map生成映射文件，查符号地址和空间占用

1.6一个最小裸机程序的骨架

#include /* 这两个符号由链接脚本提供，声明成外部符号即可使用 */ extern uint32_t _sdata, _edata, _sidata; extern uint32_t _sbss, _ebss; int main(void); /* 由应用提供，启动代码只负责调用 */ void Reset_Handler(void) { /* 1. 复制 .data：从 Flash 的加载地址搬到 RAM */ uint32_t *src = &_sidata; for (uint32_t *dst = &_sdata; dst < &_edata; ) { *dst++ = *src++; } /* 2. 清零 .bss */ for (uint32_t *dst = &_sbss; dst < &_ebss; ) { *dst++ = 0; } /* 3. 进入 C 世界 */ main(); for (;;) { } /* main 不允许返回 */ }
工程习惯

实际工程里这段通常由厂商提供的 startup_*.s 完成，还会初始化时钟、FPU、看门狗。你不需要背汇编，但必须知道它做了哪几件事——否则“全局变量初值不对”“未初始化变量不是 0”这类问题会很难查。

参考答案与思路

2. RAM 掉电丢失，烧录器只能把数据写进非易失的 Flash；运行时才把初值复制到 RAM，因为变量需要可写。

3. 所有未显式初始化的全局/静态变量，以及显式初始化为 0 的变量。C 标准保证它们是 0；如果没清零，它们会是上电后的随机值（或上一次复位前的残留）。

4. text 是代码和常量，放 Flash；data 是已初始化且非 0 的全局/静态变量，运行时占 RAM（初值占 Flash）；bss 是零初始化变量，只占 RAM，不占 Flash 镜像。

自测：启动代码必须把 .data 段从 Flash 复制到 RAM，根本原因是？

全局变量的初值必须保存在非易失存储器里（否则掉电就没了），但程序运行时要能修改它们，所以只能把初值放在 Flash，启动时复制到 RAM。

本讲小结

  • MCU 没有操作系统代劳，启动代码负责建立 C 的运行环境。
  • 五步：取向量表 → Reset_Handler → 复制 .data → 清零 .bss → 调用 main。
  • 地址空间统一映射 Flash、SRAM 和外设，指针可以指向硬件。
  • 链接脚本决定段的地址；> RAM AT > FLASH 解释了为什么要复制。
  • 交叉编译要选对 -mcpu、启动文件和链接脚本。
