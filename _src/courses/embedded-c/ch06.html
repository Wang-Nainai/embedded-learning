6.1变量到底落在哪一段

写法段占用说明
int g = 1;.dataFlash 存初值 + RAM 占 4 字节已初始化且非 0
int g; 或 int g = 0;.bss只占 RAM启动时清零，不占 Flash 镜像
const int t[] = {...};.rodata（通常）Flash是否真的不占 RAM 要看链接脚本
void f(void){ int x; }栈RAM函数返回即失效
static int s;（函数内）.bssRAM活到程序结束
malloc(n)堆RAM嵌入式里常被禁用或限制大小

在资源紧张的 MCU 上，“这个变量占不占 RAM”比“它是什么类型”更重要。一张 1 KB 的 const 表如果被放进 .data，就会白白吃掉 1 KB SRAM。

6.2对齐规则：三条就够

成员对齐　每个成员的偏移必须是它自身对齐要求的整数倍。例如 int 要求 4 字节对齐，偏移只能是 0、4、8……
结构体对齐　结构体整体的对齐等于所有成员中最大的对齐要求。
末尾补齐　结构体总大小必须是整体对齐的整数倍，以便数组中相邻元素仍然对齐。
#include #include struct A { char a; /* 偏移 0，占 1 字节 */ /* 3 字节填充 */ int b; /* 偏移 4 */ short c; /* 偏移 8 */ /* 2 字节填充（总大小要是 4 的倍数） */ }; struct B { int b; /* 0 */ short c; /* 4 */ char a; /* 6 */ /* 1 字节填充 */ }; int main(void) { printf("A: size=%zu a=%zu b=%zu c=%zu\n", sizeof(struct A), offsetof(struct A, a), offsetof(struct A, b), offsetof(struct A, c)); printf("B: size=%zu b=%zu c=%zu a=%zu\n", sizeof(struct B), offsetof(struct B, b), offsetof(struct B, c), offsetof(struct B, a)); return 0; } A: size=12 a=0 b=4 c=8 B: size=8 b=0 c=4 a=6

同样的三个成员，只是换了顺序，大小从 12 变成 8。把大的成员放前面，通常能减少填充——这是嵌入式里很实用的一个小技巧。

动手看

结构体布局计算器

依次添加成员，观察偏移、填充和总大小。再切换“紧凑布局”，看填充消失后会发生什么。

紧凑布局用 __attribute__((packed)) 或 #pragma pack(1) 实现，代价是成员可能落在非对齐地址上。

6.3紧凑布局：省了空间，付出了什么

struct __attribute__((packed)) Frame { uint8_t type; /* 0 */ uint32_t value; /* 1，未对齐 */ uint16_t crc; /* 5，未对齐 */ }; /* sizeof = 7 */
代价说明
访问变慢编译器要把一次 32 位访问拆成多次字节访问再拼起来。
可能硬件异常Cortex-M0、部分 RISC-V 配置不支持非对齐访问，直接 HardFault。
不能取成员地址当普通指针&frame.value 是“可能未对齐的指针”，解引用是未定义行为。
标准之外packed 是编译器扩展，不是 C 标准语法。
工程习惯

解析协议时，推荐“按字节读 + 显式组装”，而不是把接收缓冲区强制转换成 packed 结构体。前者可移植、可测试，也不受对齐影响：

uint32_t value = ((uint32_t)buf[1] << 24) | ((uint32_t)buf[2] << 16) | ((uint32_t)buf[3] << 8) | (uint32_t)buf[4];

6.4结构体不是字节流

下面这段代码在本机可能“能用”，换平台就错：

struct Reading { uint16_t id; float value; }; struct Reading r = {1, 23.5f}; send(fd, &r, sizeof r); /* 三个问题 */
  • 填充：id 后可能有 2 字节填充，内容不确定，会一起发出去。
  • 字节序：id 和 float 的字节顺序取决于发送方。
  • 浮点格式：IEEE 754 是事实标准，但并非所有平台都相同；对齐和大小也可能不同。
#include #include /* 明确的线格式：大端，id 2 字节 + value 4 字节 IEEE754 */ void encode_reading(uint8_t out[6], uint16_t id, float value) { uint32_t bits; memcpy(&bits, &value, sizeof bits); /* 取浮点的位模式 */ out[0] = (uint8_t)(id >> 8); out[1] = (uint8_t)(id); out[2] = (uint8_t)(bits >> 24); out[3] = (uint8_t)(bits >> 16); out[4] = (uint8_t)(bits >> 8); out[5] = (uint8_t)(bits); }
标准怎么说

标准只保证结构体成员的顺序与声明一致，不保证没有填充，也不规定填充的内容。把结构体按字节发送，等于把“本平台的布局细节”泄露到协议里。

6.5用 offsetof 和断言锁住布局

#include #include struct Header { uint8_t version; uint8_t type; uint16_t length; uint32_t seq; }; /* 如果编译器插入了意料之外的填充，这里会编译失败 */ _Static_assert(offsetof(struct Header, length) == 2, "length 必须在偏移 2"); _Static_assert(offsetof(struct Header, seq) == 4, "seq 必须在偏移 4"); _Static_assert(sizeof(struct Header) == 8, "Header 必须是 8 字节");

这类断言在跨平台工程里价值极高：它把“我以为的布局”变成“编译器必须接受的布局”。一旦换芯片或换编译器导致布局变化，编译期就会报错，而不是等到通信对不上。

  3. 为什么 packed 结构体的成员不能直接取地址传给需要对齐指针的函数？
  4. 设计一个 6 字节的线格式，包含 1 字节类型、1 字节标志、2 字节序号、2 字节校验，写出编码函数。
参考答案与思路

1. a 偏移 0；b 需要 8 对齐，偏移 8；c 偏移 16；总大小补齐到 24。

2. double b; char a; char c; → 偏移 0、8、9，总大小 16。

3. 因为成员可能位于非对齐地址，而很多架构（或编译器的向量化/宽访问）要求指针对齐；通过这种指针访问是未定义行为，可能触发硬件异常。

4. 固定大端：out[0]=type; out[1]=flags; out[2]=seq>>8; out[3]=seq; out[4]=crc>>8; out[5]=crc;。

自测：struct { char a; int b; } 在 4 字节对齐平台上 sizeof 是多少？

a 在 0，b 需要 4 对齐所以在 4，占 4–7；总大小 8，正好是 4 的倍数，不需要再补齐。

本讲小结

  • 变量落在哪个段，决定了它占 Flash 还是 RAM。
  • 对齐三规则：成员偏移对齐、结构体按最大对齐、末尾补齐。
  • 调整成员顺序可以减少填充；packed 省空间但可能牺牲速度与可移植性。
  • 结构体不能直接当字节流传输，必须显式序列化。
  • 用 offsetof + _Static_assert 锁住布局假设。
