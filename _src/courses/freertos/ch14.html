14.1需求与任务划分

目标：每 10 ms 采一次传感器，做滑动平均，打包后通过串口/网络发出；同时监控系统健康（队列丢弃、栈余量、堆余量），异常时进入安全状态。

任务划分（优先级数值越大越高）
任务优先级周期/触发最坏执行职责
sensor410 ms 周期1.5 ms读 ADC，写入原始队列
process3队列到达2 ms滤波、换算、打包
comm2队列到达8 ms（含阻塞发送）发送帧，处理重试
monitor11 s 周期0.5 ms统计、健康检查、喂狗

优先级按“周期越短越高”分配。comm 的最坏执行最长，所以放在 process 之下；即使它阻塞，也不会拖住采样。

14.3核心代码骨架

工程习惯

下面的代码是目标板结构示例，依赖 FreeRTOS 与具体硬件接口，未在主机上编译验证。它展示的是任务划分、队列策略与错误处理方式，不是可直接烧录的完整工程。

#include "FreeRTOS.h" #include "task.h" #include "queue.h" #include "event_groups.h" #define Q_RAW_LEN 8 #define Q_TX_LEN 4 typedef struct { uint16_t raw; uint32_t t_ms; } sample_t; typedef struct { int16_t value; uint32_t t_ms; uint8_t seq; } frame_t; static QueueHandle_t g_q_raw, g_q_tx; static EventGroupHandle_t g_health; static volatile uint32_t g_drop_raw, g_drop_tx; #define HEALTH_SENSOR (1u << 0) #define HEALTH_PROC (1u << 1) #define HEALTH_COMM (1u << 2) static void sensor_task(void *arg) { (void)arg; TickType_t last = xTaskGetTickCount(); for (;;) { sample_t s = { .raw = adc_read(), .t_ms = (uint32_t)xTaskGetTickCount() }; /* 采样不能被阻塞太久：最多等 2 ms，满则丢弃并计数 */ if (xQueueSend(g_q_raw, &s, pdMS_TO_TICKS(2)) != pdPASS) { g_drop_raw++; } xEventGroupSetBits(g_health, HEALTH_SENSOR); vTaskDelayUntil(&last, pdMS_TO_TICKS(10)); } } static void process_task(void *arg) { (void)arg; static int32_t window[8]; static size_t idx; sample_t s; for (;;) { if (xQueueReceive(g_q_raw, &s, portMAX_DELAY) != pdPASS) { continue; } window[idx++ % 8] = s.raw; int32_t sum = 0; for (size_t i = 0; i < 8; i++) { sum += window[i]; } frame_t f = { .value = (int16_t)(sum / 8), .t_ms = s.t_ms, .seq = (uint8_t)idx }; if (xQueueSend(g_q_tx, &f, pdMS_TO_TICKS(5)) != pdPASS) { g_drop_tx++; } xEventGroupSetBits(g_health, HEALTH_PROC); } } static void comm_task(void *arg) { (void)arg; frame_t f; for (;;) { if (xQueueReceive(g_q_tx, &f, portMAX_DELAY) != pdPASS) { continue; } /* 发送可能阻塞：允许 50 ms，失败则重试一次 */ if (link_send(&f, sizeof f, pdMS_TO_TICKS(50)) != 0) { (void)link_send(&f, sizeof f, pdMS_TO_TICKS(50)); } xEventGroupSetBits(g_health, HEALTH_COMM); } } static void monitor_task(void *arg) { (void)arg; const EventBits_t all = HEALTH_SENSOR | HEALTH_PROC | HEALTH_COMM; for (;;) { vTaskDelay(pdMS_TO_TICKS(1000)); EventBits_t bits = xEventGroupClearBits(g_health, all); size_t heap_min = xPortGetMinimumEverFreeHeapSize(); if ((bits & all) == all && heap_min > 1024) { watchdog_feed(); /* 全部健康才喂狗 */ } else { enter_safe_mode(bits, heap_min); /* 记录哪一项不健康 */ } } }

14.4队列长度与丢弃策略

队列长度满时策略理由
q_raw8丢弃新样本，计数采样是周期性的，旧数据比新数据更没价值；不能阻塞采样
q_tx4丢弃新帧，计数通信拥塞时保留最近的几帧，避免无限积压

两个队列都不阻塞生产者太久：采样任务最多等 2 ms，处理任务最多等 5 ms。超过就丢弃并计数，由监控任务上报。这比“无限等待”更可控。

14.5时序与可调度性检查

任务周期最坏执行CPU 占比
sensor10 ms1.5 ms15%
process10 ms（跟随采样）2.0 ms20%
comm约 10 ms8.0 ms（含阻塞）取决于链路
monitor1000 ms0.5 ms<1%
idle——剩余

注意 comm 的 8 ms 里大部分是“阻塞等待发送完成”，并不占 CPU。真正要算的是CPU 占用，不是墙上时间。如果 comm 的发送是忙等，就会把 CPU 吃光——这也是为什么驱动要提供阻塞式/中断式发送。

易错

把所有任务都设成高优先级，等于没有优先级。优先级的意义是“在冲突时谁先运行”，如果每个任务都“很重要”，系统就无法在过载时保住关键任务。

14.6测试与验收

  • 空载：4 个任务都运行，CPU 占用 < 30%
  • 满负载：采样 10 ms 不丢帧，队列丢弃计数为 0
  • 通信断开：q_tx 满后按策略丢弃，系统不卡死，恢复后能继续
  • 注入错误：传感器返回非法值，process 不崩溃
  • 连续运行 24 h：堆最小值不持续下降，无栈溢出
  • 看门狗：人为挂起 comm 任务，系统应在超时后复位

  2. 给 comm 任务加“指数退避重试”，最多 3 次。

参考答案与思路

1. 长度 2 只能吸收 20 ms 的抖动；只要 process 偶尔超过 20 ms，就会开始丢弃。适合“允许丢帧、但要低延迟”的场景。

2. 保存 backoff，失败后 vTaskDelay(backoff)，backoff = min(backoff*2, MAX)；成功则复位。注意 comm 阻塞期间 q_tx 会积压，要配合丢弃策略。

3. 单独建一个配置队列，process 在每次循环里非阻塞地检查配置队列；或者用事件组置位 + 共享配置结构（加互斥量）。

4. 开 configGENERATE_RUN_TIME_STATS，运行典型负载后打印统计，和 14.5 的估算对比。

自测：采样任务在队列满时应该？

采样任务的第一职责是“按时采样”。无限等待会破坏周期；队列本身不支持覆盖。正确做法是短超时 + 丢弃 + 计数，由监控任务上报。

本讲小结

  • 任务划分按“周期 + 职责”，优先级按截止期分配。
  • 队列长度与丢弃策略要显式设计，不能无限等待。
  • 监控任务旁路观察，全部健康才喂狗。
  • CPU 占用要按“实际执行时间”算，不是墙上时间。
  • 测试要覆盖空载、满载、断链、错误注入与长时间运行。
