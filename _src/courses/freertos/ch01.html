1.1一个大循环能走多远

大多数裸机程序长这样：

int main(void) { board_init(); for (;;) { read_sensor(); /* 可能要等 10 ms */ update_display(); /* 可能要 30 ms */ handle_uart(); /* 数据来了才需要处理 */ feed_watchdog(); } }

它能工作，但有三个结构性瓶颈：

阻塞传染

任何一步等待，后面所有逻辑都被推迟。显示刷新 30 ms，串口响应就可能晚 30 ms。

响应不确定

最坏响应时间等于整个循环的时间，而不是某个事件的处理时间。

状态耦合

各模块共享一个大循环，靠全局变量和标志沟通，越加越乱。

1.2RTOS 提供的四样东西

能力解决什么问题FreeRTOS 中的对应物
并发抽象把“同时要做的事”写成独立函数任务（task）
调度决定现在运行谁，让等待不再阻塞别人调度器、优先级、tick
通信任务之间安全地传数据队列、任务通知、事件组
同步保护共享资源、等待事件信号量、互斥量、临界区

注意：RTOS 不提供“无限资源”，也不提供“硬实时保证”。它提供的是可分析的结构：你能说清每个任务的周期、优先级、阻塞点和最坏执行时间。

工程习惯

先问“需不需要”，再问“用哪个”。一个 8 位 MCU、只有 2 KB RAM、逻辑就是“读传感器 → 串口发出去”，用 RTOS 往往得不偿失。反过来，如果有 3 个以上独立时序、需要阻塞等待、需要协议栈，RTOS 通常比手写状态机更省心。

1.4什么时候不需要 RTOS

  • 逻辑是严格的单一时序，没有并发等待。
  • RAM 极度紧张，任务栈的开销无法承受。
  • 响应时间要求可以用“中断 + 主循环”满足，且可预测。
  • 团队不熟悉并发调试，引入 RTOS 反而增加风险。

反过来，出现下面任意两条，就该认真考虑 RTOS：多个独立周期、需要阻塞等待、通信协议栈、需要优先级（紧急事件优先处理）、代码需要长期维护和扩展。

1.5最小可运行结构

#include "FreeRTOS.h" #include "task.h" static void blink_task(void *arg) { (void)arg; for (;;) { gpio_toggle(LED_PIN); vTaskDelay(pdMS_TO_TICKS(500)); } } int main(void) { board_init(); if (xTaskCreate(blink_task, "blink", 128, NULL, 2, NULL) != pdPASS) { for (;;) { } /* 创建失败：停在这里，便于调试 */ } vTaskStartScheduler(); /* 正常情况下不会返回 */ for (;;) { } }
实现细节

vTaskStartScheduler() 会创建空闲任务（idle task），如果启用了软件定时器还会创建定时器守护任务。空闲任务优先级最低（0），负责释放被删除任务的内存、执行 idle hook。它必须始终有机会运行，否则低优先级清理工作永远做不了。

自测：下面哪一项不是 RTOS 直接提供的？

RTOS 提供调度机制，但不保证你的任务一定能在截止时间内完成。最坏执行时间要靠测量、分析和设计（优先级、任务划分、临界区长度）来保证。

本讲小结

  • 裸机大循环的三个瓶颈：阻塞传染、响应不确定、状态耦合。
  • RTOS 提供任务、调度、通信、同步四类能力。
  • 代价是 RAM/Flash、切换开销和并发调试复杂度。
  • 是否需要 RTOS，取决于并发等待与可维护性，而不是“看起来高级”。
