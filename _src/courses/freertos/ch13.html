13.1四种“卡住”，四种根因

故障典型现象根因先查什么
死锁相关任务全部停住，CPU 可能空闲互相等对方持有的锁加锁顺序、是否有超时
优先级反转高优先级任务偶尔延迟很久中优先级任务抢占持锁的低优先级任务持锁时间、是否用互斥量
饥饿低优先级任务长期不运行高优先级任务一直就绪CPU 利用率、优先级设计

13.2死锁的排查

死锁时系统往往“安静地停住”：没有崩溃，没有日志，只是什么都不发生。排查步骤：

确认是否死锁　用调试器暂停，看各任务卡在哪个函数；如果都卡在 xSemaphoreTake，高度怀疑。
找锁的持有者　FreeRTOS 的互斥量有所有者；检查是谁拿了锁却没释放。
看加锁顺序　两个任务是否以相反顺序获取两把锁。
加超时与日志　把 portMAX_DELAY 改成有限超时，记录失败点。
/* 统一顺序：永远先 m1 后 m2 */ if (xSemaphoreTake(m1, pdMS_TO_TICKS(50)) != pdTRUE) { return ERR_BUSY; } if (xSemaphoreTake(m2, pdMS_TO_TICKS(50)) != pdTRUE) { xSemaphoreGive(m1); /* 拿不到第二把，释放第一把 */ return ERR_BUSY; } /* ... */ xSemaphoreGive(m2); xSemaphoreGive(m1);

13.3饥饿与 CPU 利用率

如果高优先级任务永远就绪（例如一个没有阻塞的 for(;;) 循环），低优先级任务永远得不到 CPU。这不是 bug，是设计问题。

  • 每个任务都必须有阻塞点（延时、等队列、等信号量）。
  • 计算密集型任务要主动让出，或放到最低优先级。
  • 用运行时统计看每个任务占了多少 CPU。
/* 需要 configGENERATE_RUN_TIME_STATS = 1，并提供高精度计时 */ char buf[512]; vTaskGetRunTimeStats(buf); /* 每个任务的运行时间与占比 */ printf("%s\n", buf); vTaskList(buf); /* 任务状态、优先级、剩余栈、序号 */ printf("%s\n", buf);
实现细节

vTaskGetRunTimeStats 需要一个比 tick 更细的计时源（通常是另一个定时器），通过 portCONFIGURE_TIMER_FOR_RUN_TIME_STATS 和 portGET_RUN_TIME_COUNTER_VALUE 接入。只有 tick 计时的话，分辨率太粗。

13.4栈溢出的现象与定位

栈溢出最迷惑人的地方是它不一定立刻崩溃：溢出的数据可能踩到相邻任务的栈或 TCB，表现为“某个无关变量变了”“任务突然不跑了”。

配置行为优缺点
configCHECK_FOR_STACK_OVERFLOW = 1切换时检查栈指针是否越界开销小，但只能发现“已经越界”
= 2 additionally 检查栈末尾的魔术字更可靠，需要预填模式
高水位运行后查看剩余量不能发现瞬时峰值
工程习惯

发布版本也保留栈溢出钩子，但钩子里不要 printf（栈可能已经坏了）。最稳的做法是：点亮故障灯、把任务名写入保留 RAM（不掉电区域）、触发看门狗复位。

13.5configASSERT 与看门狗

/* 在 FreeRTOSConfig.h 中定义，参数非法时立刻停机 */ #define configASSERT(x) do { if (!(x)) { taskDISABLE_INTERRUPTS(); \ fault_handler(__FILE__, __LINE__); } } while (0)

configASSERT 能抓住大量“参数非法、优先级越界、队列句柄为空”的问题。开发阶段一定打开；发布版本可以保留（停机 + 记录），也可以改成复位。

看门狗是最后一道防线：监控任务定期“喂狗”，如果某个关键任务卡死，系统自动复位。注意喂狗应该在所有关键任务都健康时进行，而不是随便找个最低优先级任务喂。

13.6五个常见误区

误区事实
“优先级越高，系统越实时”优先级只决定谁先运行；实时性取决于最坏执行时间与阻塞时间
“加了互斥量就不会有并发问题”还要考虑死锁、持锁时间、ISR 访问
“volatile 能替代锁”它不保证原子性，也不保证顺序
“队列越长越安全”长队列增加延迟和 RAM；过载时照样满
“RTOS 会自动保证实时”它只提供机制，分析和设计仍要自己做
动手练习 · 第 13 讲
  1. 系统运行几分钟后“整体卡住”，如何判断是死锁还是饥饿？
  2. 高优先级任务偶发延迟 200 ms，可能是什么原因？
  3. 如何用运行时统计证明某个任务占用了 95% CPU？
  4. 设计一个“关键任务都健康才喂狗”的方案。
参考答案与思路

1. 暂停看各任务栈：都卡在等锁 → 死锁；高优先级任务一直 Running、低优先级从未运行 → 饥饿。

2. 优先级反转（持锁任务被中优先级抢占）、临界区过长、中断关闭过久、队列/内存分配阻塞。

3. 开 configGENERATE_RUN_TIME_STATS，调用 vTaskGetRunTimeStats，看该任务的百分比与绝对时间。

4. 每个关键任务定期置一个事件位；监控任务等齐所有位后喂狗并清位；任何一个任务超时未置位，就不喂狗，让系统复位。

自测：低优先级任务长期得不到运行，最可能的原因是？

这是典型的饥饿：高优先级任务没有阻塞点，调度器永远选它。解决办法是给高优先级任务加阻塞点，或重新评估优先级与任务划分。

本讲小结

  • 死锁、反转、饥饿、栈溢出都会表现成“卡住”，但根因不同。
  • 死锁靠加锁顺序、超时与日志定位。
  • 饥饿靠运行时统计与“每个任务都要阻塞”来避免。
  • 栈溢出要用高水位 + 溢出钩子 + 最坏路径测试。
  • configASSERT 与看门狗是最后两道防线。
