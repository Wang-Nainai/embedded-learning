11.1软件定时器不是硬件定时器

FreeRTOS 的软件定时器由定时器守护任务（timer service task）统一管理。定时器到期时，守护任务调用你的回调。回调运行在任务上下文，不是中断上下文。

软件定时器硬件定时器
精度受 tick 与守护任务调度影响可达纳秒级
数量几乎不限（受 RAM 限制）受外设数量限制
回调上下文守护任务中断
适用超时、心跳、周期性业务PWM、输入捕获、精确采样

11.2创建与启动

#include "FreeRTOS.h" #include "timers.h" static TimerHandle_t g_heartbeat; static TimerHandle_t g_timeout; static void heartbeat_cb(TimerHandle_t t) { (void)t; gpio_toggle(LED_PIN); /* 只做轻量工作 */ } static void timeout_cb(TimerHandle_t t) { /* 通过定时器 ID 区分是哪个实例 */ int conn_id = (int)(intptr_t)pvTimerGetTimerID(t); connection_mark_timeout(conn_id); } void app_init(void) { /* 周期 500 ms，自动重载 */ g_heartbeat = xTimerCreate("hb", pdMS_TO_TICKS(500), pdTRUE, NULL, heartbeat_cb); /* 一次性 3 s 超时 */ g_timeout = xTimerCreate("to", pdMS_TO_TICKS(3000), pdFALSE, (void *)(intptr_t)1, timeout_cb); configASSERT(g_heartbeat != NULL && g_timeout != NULL); xTimerStart(g_heartbeat, 0); /* 0：不等待命令队列 */ xTimerStart(g_timeout, 0); }
实现细节

xTimerStart 本身是把“启动命令”发到定时器命令队列，由守护任务执行。第二个参数是等待队列空位的超时。如果在调度器启动前调用，命令会排队，等守护任务运行后处理。

11.3回调里不能做什么

不要做原因替代
阻塞（延时、等信号量）会卡住整个守护任务，所有定时器都延迟置标志、发队列、发通知
长时间计算同上把工作交给专用任务
删除/修改正在执行的定时器可能死锁或行为未定义发命令给其他任务处理
调用 vTaskDelay守护任务被阻塞用状态机 + 下次到期
/* 正确：回调运行在守护任务上下文，用任务版 API；只发通知，处理在任务里 */ static void sample_timer_cb(TimerHandle_t t) { (void)t; xTaskNotifyGive(g_sample_task); }
易错

在定时器回调里用非 0 阻塞时间调用 xTimerStop 停自己，会让守护任务等待自己处理完命令，形成死锁。要停止自己，应使用阻塞时间为 0 的调用，或发一个命令给其他任务，由它来停。

11.4精度与漂移

周期定时器的“周期”是两次到期之间的 tick 数，但回调执行时间、守护任务被更高优先级任务抢占，都会让实际间隔变长。它不累积相对误差（内核按绝对到期时间排队），但会有抖动。

  • 需要毫秒级稳定周期：用硬件定时器中断 + 任务通知。
  • 需要“几秒后提醒”：软件定时器足够。
  • 需要大量定时器：软件定时器比硬件定时器更省外设。

11.5配置项

#define configUSE_TIMERS 1 #define configTIMER_TASK_PRIORITY 3 /* 守护任务优先级 */ #define configTIMER_QUEUE_LENGTH 10 /* 命令队列长度 */ #define configTIMER_TASK_STACK_DEPTH 256 /* 守护任务栈（字） */

守护任务优先级要高于使用定时器的普通任务，否则命令和回调都会被延迟；但也不要比硬实时任务高，否则会抢占关键控制。

自测：软件定时器的回调运行在哪个上下文？

所有软件定时器共享一个守护任务，回调在其中依次执行。这也是“回调不能阻塞”的根本原因。

本讲小结

  • 软件定时器由守护任务统一调度，精度受 tick 影响。
  • 回调运行在任务上下文，不能阻塞、不能长时间计算。
  • 启动/停止都是向命令队列发送请求。
  • 大量低精度定时用软件定时器，精确时序用硬件定时器。
