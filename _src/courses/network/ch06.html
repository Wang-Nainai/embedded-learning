6.1TCP 提供的是“字节流”，不是“消息”

TCP 保证的是：你写进去的字节，会按顺序、不重复、不丢失地到达对方。它不保留“消息边界”——你分三次写 100 字节，对方可能一次读到 300 字节，也可能分十次读到。

易错

“TCP 会粘包”是一个不准确的说法。TCP 根本没有“包”的概念，它只有字节流。所谓粘包/拆包，是应用层没有定义消息边界造成的，解决方法是长度字段、分隔符或固定长度，而不是“让 TCP 别粘”。

6.2三次握手：确认双方都能收发

步骤方向标志作用
1客户端 → 服务器SYN我想连接，我的初始序号是 x
2服务器 → 客户端SYN + ACK同意，我的初始序号是 y，确认 x+1
3客户端 → 服务器ACK确认 y+1，连接建立

为什么不是两次？两次只能确认“客户端能发、服务器能收”，无法确认“服务器能发、客户端能收”。第三次 ACK 让服务器确认自己的 SYN 被收到。

6.3序号、确认与重传

  • 序号（seq）：本段第一个字节在字节流中的位置。
  • 确认号（ack）：期望收到的下一个字节序号，表示“这之前的所有字节都收到了”（累积确认）。
  • 超时重传：发送方等不到 ACK，按 RTO 重发。RTO 根据往返时间动态估算。
  • 快速重传：收到 3 个重复 ACK，不等超时立刻重发丢失的段。
发送方：seq=1000, len=500 → 丢失 接收方收到 seq=1500 → 回 ACK 1000 接收方收到 seq=2000 → 回 ACK 1000（重复） 接收方收到 seq=2500 → 回 ACK 1000（重复） 发送方收到 3 个重复 ACK → 立刻重发 seq=1000

6.4流量控制与拥塞控制

流量控制拥塞控制
解决什么接收方处理不过来网络中间链路拥塞
依据接收窗口 rwnd拥塞窗口 cwnd
谁决定接收方通告发送方根据丢包/延迟调整
实际发送量min(rwnd, cwnd)

拥塞控制的经典行为：慢启动（cwnd 指数增长）→ 拥塞避免（线性增长）→ 丢包时减半（AIMD）。现代算法（CUBIC、BBR）各有不同，但目标都是“尽量跑满又不压垮网络”。

6.5四次挥手与 TIME_WAIT

TCP 是全双工，两个方向要分别关闭，所以需要四次：

FIN　主动关闭方说“我没数据要发了”。
ACK　对方确认，但可能还有数据要发。
FIN　对方发完数据，也说“我发完了”。
ACK　主动关闭方确认，进入 TIME_WAIT。

TIME_WAIT 持续 2MSL（通常 60 秒），目的有两个：确保最后一个 ACK 能到达（丢了可以重发），以及让旧连接的迷路包在网络中消失，避免污染新连接。

工程习惯

服务器出现大量 TIME_WAIT 通常是“短连接太多”。可以用连接池/长连接减少，而不是简单调小 TIME_WAIT 或开 tcp_tw_reuse——后者有副作用，要理解清楚再用。

参考答案与思路

1. 两次无法让服务器确认“自己的 SYN 被客户端收到”，也无法确认客户端接收能力；三次才能双向确认。

2. 停止发送新数据，启动零窗口探测（zero window probe），定期询问窗口是否恢复。

3. 保证最后一个 ACK 能重发；让旧连接的残留包过期，避免影响新连接。

4. 应用层的问题。TCP 是字节流，不保留消息边界；需要长度字段/分隔符来分帧。

自测：TCP 的确认号表示什么？

确认号是“下一个期望的字节序号”，表示该序号之前的所有字节都已收到（累积确认）。

本讲小结

  • TCP 是可靠、有序的字节流，不保留消息边界。
  • 三次握手双向确认；四次挥手分别关闭两个方向。
  • 序号按字节编号，确认号是下一个期望字节。
  • 流量控制看接收窗口，拥塞控制看网络状况。
  • TIME_WAIT 保证可靠关闭与旧包过期。
