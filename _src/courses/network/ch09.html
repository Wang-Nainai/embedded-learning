9.1MQTT 解决“很多设备、很多订阅者”

HTTP 是“客户端问、服务器答”。如果 1000 台设备都要把数据送给 10 个订阅者，HTTP 会让每台设备分别推给每个订阅者，连接数和耦合度都爆炸。

MQTT 引入 Broker：发布者只把消息发给 Broker，订阅者只从 Broker 收。双方不需要知道对方的存在，只约定主题。

标准怎么说

MQTT 是应用层协议，跑在 TCP 之上（默认 1883，TLS 为 8883）。它不是“替代 TCP/IP 的底层传输”，也不负责 IP 寻址、路由和可靠字节流——那些仍然是 TCP/IP 的工作。

9.2主题与通配符

home/livingroom/temperature home/kitchen/temperature device/esp32-001/status 订阅： home/+/temperature + 匹配一层 home/# # 匹配多层（必须放在末尾）

主题是大小写敏感的，用 / 分层。不要用 # 订阅所有主题——消息量大时会压垮设备和 Broker。

9.3QoS：保证到什么程度

QoS语义交互可能的结果
0最多一次（发完就忘）PUBLISH可能丢，不会重复
1至少一次PUBLISH → PUBACK不丢，但可能重复（需要应用去重）
2恰好一次PUBLISH → PUBREC → PUBREL → PUBCOMP不丢不重，开销最大
易错

QoS 2 的“恰好一次”是在 Broker 与客户端之间的语义，不覆盖端到端业务。如果发布者重连后重发、或者业务本身重复执行，仍然可能产生重复副作用。关键操作要自己做幂等（例如带消息 ID 去重）。

9.4保留消息、遗嘱消息与会话

功能作用注意
RetainedBroker 保留该主题最后一条消息，新订阅者立刻收到只保留一条；发空载荷可清除
Will客户端异常断开时，Broker 代发一条消息正常断开（DISCONNECT）不触发
Clean Session为 0 时 Broker 保留订阅与离线消息MQTT 5 用 Session Expiry 替代
Keep Alive客户端定期 PING，维持连接与 NAT 映射超时 1.5 倍未收到任何包则断开

发布、订阅与 QoS 流程

选择 QoS，点“发布”，看消息经过 Broker 到达订阅者时需要几次交互。再试试保留消息与遗嘱消息。

QoS 1 可能重复，QoS 2 用四次交互换“不重”；保留消息让新订阅者立刻拿到最后状态。

9.5一个设备端的连接参数

Broker broker.example.com:8883（TLS） ClientID esp32-001（必须唯一） Username 设备 ID Password Token / 证书 KeepAlive 60 秒 Clean 0（保留会话） Will device/esp32-001/status = "offline"（QoS 1, retained）
工程习惯

ClientID 重复会导致两个客户端互相踢下线，表现为“设备频繁掉线”。量产设备要用 MAC/芯片 ID 生成唯一 ClientID，并避免在重连时随机变化（否则会话丢失）。

参考答案与思路

1. 例如 device/<id>/status、device/<id>/telemetry、device/<id>/cmd；控制指令用 QoS 1 + 消息 ID 去重。

2. 发布者没收到 PUBACK 会重发，Broker 可能已处理过。应用层用消息 ID/时间戳做幂等。

3. 保留消息让新订阅者立刻获得最新状态；遗嘱消息让系统知道设备异常离线。

4. MQTT 依赖 TCP 提供可靠字节流与连接管理，自己只负责消息路由与语义；它不定义 IP 寻址、路由、链路传输。

自测：MQTT QoS 1 的语义是？

QoS 1 用 PUBACK 确认，没收到就重发，所以“至少一次”，代价是可能重复；QoS 2 才做到“恰好一次”。

本讲小结

  • MQTT 用 Broker 和主题解耦发布者与订阅者。
  • QoS 0/1/2 分别是最多一次、至少一次、恰好一次。
  • 保留消息、遗嘱消息、会话分别解决状态、离线通知与断线续传。
  • MQTT 跑在 TCP 之上，不是传输层协议。
  • ClientID 必须唯一，关键业务要自己做幂等。
