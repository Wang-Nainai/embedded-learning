5.1端口与套接字

IP 地址把数据送到主机，端口把数据送到主机上的某个程序。端口是 16 位整数（0–65535）：

范围名称说明
0–1023知名端口HTTP 80、HTTPS 443、DNS 53、MQTT 1883
1024–49151注册端口厂商/应用注册使用
49152–65535临时端口客户端发起连接时由系统分配

套接字（socket）通常指“IP + 端口 + 协议”的组合，例如 192.168.1.10:50000 TCP。一条 TCP 连接由四元组唯一确定：源 IP、源端口、目的 IP、目的端口。

5.2UDP 只做四件事

UDP 的头部只有 8 字节：源端口、目的端口、长度、校验和。它提供的能力非常有限：

提供

它做的

  • 端口复用（区分应用）
  • 可选的校验和
  • 保留消息边界（一次发 = 一个数据报）
  • 支持广播/组播
不提供

它不做的

  • 不建连、不握手
  • 不确认、不重传
  • 不保证顺序
  • 不控制拥塞
标准怎么说

IPv4 中 UDP 校验和是可选的（全 0 表示不校验），IPv6 中必须计算。校验和覆盖伪头部（源/目的 IP、协议号、UDP 长度）+ UDP 头 + 数据，所以能发现 IP 地址错误。

5.3什么时候选 UDP

场景为什么 UDP
DNS 查询一问一答，包小，重发比建连快
DHCP客户端还没有 IP，无法建 TCP；用广播
实时音视频宁可丢一帧，也不要等重传造成卡顿
游戏状态同步只关心最新状态，旧包没价值
局域网设备发现广播/组播，TCP 不支持
CoAP / LwM2M受限设备，开销小

“UDP 不可靠”不等于“不能用”。很多协议在 UDP 之上自己做序号、确认、重传（QUIC 就是典型），把可靠性做成可定制的。

5.4本机观察 UDP

# 终端 1：监听 9999 端口 nc -u -l 9999 # 终端 2：发送一个数据报 echo "hello udp" | nc -u 127.0.0.1 9999 # 查看本机 UDP 端口 ss -lun # Linux netstat -anu # Windows / macOS hello udp
工程习惯

UDP 没有连接状态，防火墙/ NAT 的超时更短。设备如果长时间不发数据，NAT 映射可能被回收，导致“服务器发不进来”。需要心跳（keepalive）维持映射。

5.5UDP 上的可靠性要自己补

如果业务需要“不丢、不重、有序”，又必须用 UDP（例如实时性要求高、或需要组播），就要自己实现：

  • 序号 + 确认 + 超时重传（或 NACK）。
  • 去重（同一序号只处理一次）。
  • 乱序缓冲（按序号重组）。
  • 拥塞控制（否则会压垮网络）。

这也是 QUIC 做的事情——它把 TCP 的可靠性 + TLS 加密搬到了 UDP 之上，避免了 TCP 的队头阻塞。

参考答案与思路

1. 源 IP、源端口、目的 IP、目的端口（加协议）。

2. 查询小、一问一答，UDP 省去建连开销；超时重发比 TCP 握手更快。大响应/区域传送会用 TCP。

3. 能。校验和覆盖伪头部，其中包含源/目的 IP。

4. NAT 映射可能超时被删除，服务器再发数据就找不到内网设备；需要周期性心跳维持。

自测：UDP 相比 TCP 缺少下面哪一项？

UDP 有端口和校验和，但不提供确认、重传、排序、流量控制与拥塞控制——这些正是 TCP 的核心。

本讲小结

  • 端口区分主机上的应用，套接字由 IP+端口+协议标识。
  • UDP 头部只有 8 字节，保留消息边界，支持广播/组播。
  • UDP 不保证送达、顺序与拥塞控制。
  • 实时、短查询、广播场景优先 UDP。
  • 需要可靠性时，在应用层自己补或改用 QUIC。
